### 1.2 Статусная модель — 03 §8

**Статус работы слушателя** (6): Не сдано → Сдано → На взаимопроверке → Взаимопроверка завершена,
ожидает итогового результата → Итоговый результат выставлен; отдельная ветка — Возвращено на
доработку. Максимально переиспользуются существующие статусы ПЗ (04 §10), новые статусы — только
если текущих недостаточно.

**Статус назначенной проверки** (5): Назначена → В работе → Проверена; отдельно — Приостановлена
(при возврате работы на доработку) и Отменена (проверка снята/больше не требуется). 04 §16 прямо
говорит, что отдельная вторая статусная модель не обязательна, если сценарий покрывается
существующими статусами ПЗ и локальными состояниями интерфейса — то есть 03 §8.3 из ТЗ проработки
может не материализоваться 1:1 в API; кейсы 067–069 пишут это как целевое поведение по 03, с риском
ревизии при технической реализации (см. §6 «Риски»).

| Тип | Агрегация | Кейсы |

Правила изменения формы (04 §5.2): после первой полученной peer-проверки нельзя добавлять/удалять

### 1.4 Явно вне границ (04 §16, 03 §15)

- Новый тип активности «ПЗ с взаимопроверкой» — не создаётся, используется существующий тип
  «Практическое задание» + настройка.
- Отдельный флаг «Может выставлять итоговый результат» у штатного проверяющего — по 04 не нужен
  (расхождение с 03, см. §5).
- Бизнес-механика весов критериев/вариантов — не в текущем объёме (несмотря на то что 03 §7.5
  фиксирует её как «новое требование» — 04 §16 явно снимает).
- Сценарий «Индивидуальные ПЗ в режиме самопроверки» — исключён из ТЗ целиком (03 §15), кейсов нет.
- Групповые ПЗ — взаимопроверка недоступна (097), это отдельное ограничение по итогам обсуждения
  (02 п.4), не требование исходного ТЗ.

## 2. Стратегия тестирования

**Внешних систем в этой миссии нет** (в отличие от парной интеграции с МТС Линк) — вся
функциональность внутренняя, поэтому основной объём автотестов планируется API+UI на будущей
ветке с реальными данными, без моков. Уровни по кейсам: 46 автотестов (kejsy c `- Автотест:`,
nodeid уже присвоен в файлах кейсов для каркаса Этапа 3 миссии — кода пока нет), 65 ручных
(из них 20 явно заблокированы ответом заказчика, см. §4; остальные 45 — ручные по решению
Этапа 1 миссии: критерии, возврат на доработку, вид автора, отчёт, уведомления, сертификаты,
роли, журналирование — категории, не отмеченные в мисcии для автоматизации).

### 2.1 Многоролевые сценарии

Сложность плана не в API-контракте (его как такового ещё нет, только предполагаемый — см. мисcию
Этап 3), а в количестве ролей, которые нужно свести в одном тесте: автор + 2–3 слушателя-проверяющих
+ штатный проверяющий + внешний проверяющий + администратор без назначения (для 046/091). Ни одну
из этих учёток руками не заводим — тесты создают их сами:

| Роль в тесте | Как создаётся | Примечание |
|---|---|---|
| Автор работы, слушатели-проверяющие (3+) | `created_user` / сценарий `users` генератора (`test_data_generation/generate.py --scenario users`), `region_id`/роль по умолчанию, имя с префиксом `Автотест_p2p_<ts>` | Один поток, чтобы участвовать в P2P друг друга (04 §5.1/§6: p2p работает только в рамках потока) |
| Штатный проверяющий ПЗ | `created_user` с ролью «проверяющий»/«преподаватель» (сценарий `users` уже поддерживает роль «проверяющий» как системную), назначается в карточку ПЗ | Отдельно от слушателей-проверяющих потока (04 §4.2: списки не пересекаются, см. 005) |
| Администратор без назначения проверяющим | Существующий фикстурный админ, **не** добавляется в список проверяющих ПЗ | Нужен для негативных 046/091 |
| Внешний проверяющий | Не системный пользователь — создаётся вызовом P2P API (ФИО с префиксом `Автотест_`, email опционален), у генератора `test_data_generation` для него отдельного сценария нет и не нужен | Работает в отдельном browser context без авторизации (мисcия Этап 3: `external_review_page.py`) |

Пароль для системных пользователей — общий `DEFAULT_PASSWORD` (см. README §9), как и в остальных
существующих сценариях генератора; тесты не создают новые механизмы аутентификации.

### 2.2 Уровни и переиспользование

- **API** — настройки карточки/потока, распределение, агрегация, статусы, регресс (без экрана,
  быстрее и стабильнее).
- **UI** — peer-проверка слушателем (форма критериев, редактирование до подтверждения) и внешняя
  проверка по ссылке (обязательно отдельный browser context — нет авторизации).
- **Ручные** — критерии (конструктор), возврат на доработку, вид автора, отчёт PDF/Word,
  уведомления, сертификаты, роли/доступ, журналирование. Часть из них ручные не навсегда, а потому
  что заблокированы ответом заказчика (§4); часть (отчёт, уведомления, сертификаты, журналирование)
  — по решению Этапа 1 миссии как категории с низкой автоматизируемой ценностью на первом этапе
  (PDF/Word-парсинг, email, сертификаты — дорогая инфраструктура при неподтверждённых требованиях).
- Существующие Page Object (`practical_task_page.py`, `reviewer_page.py`) и тесты
  (`test_review_practical_task.py`, `test_complete_practical_task.py`, групповые/индивидуальные ПЗ)
  — образец структуры и заодно основа для регрессионных кейсов 108–111 (см. §1 табл. §1/§14).
- Окружение — `develop` (см. README §2 «Окружения»); `prod` для мутирующих P2P-тестов не
  используется (`ensure_prod_allowed`, `PROD_ALLOWED_MARKEXPR="smoke"`).

## 5. Расхождения версий 02/03/04 — вопросы аналитику

Из README (уже зафиксированы, повторены для полноты матрицы) + дополнения, найденные при
сопоставлении с кейсами:

1. **Право итогового результата.** 04 — любой штатный проверяющий; 03 — отдельный признак «Может
   выставлять итоговый результат»; 02 — верификация преподавателем. Кейсы 043–046, 092 написаны по
   04. *Вопрос аналитику:* подтверждать ли окончательно вариант 04 в постановке разработки, или
   признак из 03 всё же нужен для случая «несколько проверяющих, не все должны иметь право итога»?
2. **Внешний проверяющий: объём видимого и повторное использование ссылки.** 04 — видит список всех
   сданных работ ПЗ в потоке, ссылка многоразовая; 03/05 — видит одну работу, ссылка одноразовая на
   пару «работа — проверяющий». Кейсы 033–039 написаны по 04, что прямо противоречит
   предлагаемому в 05 варианту «персональная одноразовая ссылка для конкретной работы» (05 §6).
   *Вопрос аналитику:* 05 писался раньше или после 04 версии по этому пункту — что именно
   подтвердил заказчик на встрече?
3. **Где настройки.** 04 — критерии и штатные проверяющие в карточке, распределение в потоке; 02 —
   в карточке только флаг. Кейсы 001–006/015 — по 04.
4. **Возврат на доработку.** 04 — штатный проверяющий, повторный цикл; 03 — настройка «разрешить
   возврат», приостановка у всех; 01 — на первом этапе не использовать вовсе. Кейсы 054–061 — по
   04+03 (04 предполагает саму возможность, 03 — механику приостановки, которую 04 не отменяет).
5. **Итог без штатных проверяющих.** Вопрос заказчику №1 не отвечен; при этом 04 §9 говорит «если
   назначен хотя бы один штатный проверяющий — система итог не выставляет», подразумевая, что без
   штатных выставление возможно, но не описывает как. *Новое для аналитика:* нужно явно
   зафиксировать, может ли P2P-ПЗ вообще существовать без штатных проверяющих технически (в карточке
   поле «Проверяющие» — обязательное или нет), это отдельный вопрос от алгоритма авто-итога.
6. **04 §5.2 vs 03 §7.5 — судьба весов шкалы.** 03 фиксирует настраиваемую шкалу с весами как «новое
   требование» после комментария Максима; 04 §16 явно исключает «отдельную бизнес-механику весов
   критериев» из объёма. Кейс 007 («шкала с весом») по приоритету 04→03 формально не должен был
   тестировать вес — но написан по 03 §7.5 (детали типов критериев в 04 не расписаны, только
   упомянуты кратко). *Вопрос аналитику:* значение веса варианта шкалы входит в объём первого этапа
   или нет — 04 §16 и 04 §5.1/03 §7.5 friction.

## 6. Риски

1. **Алгоритм автоматического распределения не выбран** (вопрос №3). Кейс 027 по конструкции —
   заглушка; любой реализованный алгоритм (случайный/с выравниванием/по очереди) даст разное
   распределение при одинаковых входных данных, поэтому автотесты 023/024 проверяют инварианты
   («не больше N работ», «не своя работа»), а не конкретное распределение — это правильно и не
   требует переписывания после ответа заказчика.
2. **Версии критериев после начала проверки.** 04 §5.2 запрещает добавление/удаление критериев
   после первой peer-проверки, но не описывает версионирование формы технически (что происходит с
   уже сохранёнными ответами при правке текста критерия — 013 предполагает «не теряются», это
   предположение, не подтверждённый факт).
3. **Повторный цикл после доработки** (вопрос №7) — самый насыщенный открытыми вопросами блок (4
   вопроса из 20 заблокированных кейсов). Три конкурирующих варианта судьбы старых
   проверок/назначений — тесты 059–061 не могут быть автоматизированы до ответа, а сама логика
   возврата (054–058) тестируется вручную даже по «твёрдой» части 04, т.к. не входит в перечень
   автоматизации Этапа 1 миссии.
4. **Внешняя ссылка без авторизации — риски безопасности.** Персональная ссылка по 04 многоразовая
   и без логина — нужно отдельно проверять (уже сейчас, не дожидаясь ответа по вопросу №6):
   перебор/угадывание ссылок других внешних проверяющих (нет ли последовательных/предсказуемых
   идентификаторов — см. 038 про уникальность «по внутреннему идентификатору, не по ФИО»), доступ
   по чужой ссылке к работам другого потока/ПЗ, повторная отправка формы проверки той же работы тем
   же внешним проверяющим (05 §6: одна ссылка = одна проверка на первом этапе, но 04 говорит
   «ссылка используется повторно» — неясно, можно ли повторно отправить оценку по уже проверенной
   работе). Это не просто открытый вопрос, а потенциальная уязвимость независимо от ответа
   заказчика — стоит вынести в отдельный security-кейс на этапе разработки.
5. **Анонимность** (вопрос №9). Показ ФИО и текстовых комментариев проверяющих автору работы не
   подтверждён — если решение окажется «анонимно», часть UI (переиспользуемый `reviewer_page.py`)
   потребует скрытия полей, которые до этого были видны в других ПЗ-сценариях без взаимопроверки.
6. **Производительность при N×M назначениях.** Автораспределение (023) и матрица «работ на
   слушателя» × «минимум проверок на работу» растут квадратично с размером потока; кейсы не
   проверяют производительность явно — нагрузочный сценарий (крупный поток, десятки слушателей)
   не входит в объём Этапа 1 и должен быть заведён отдельно после выбора алгоритма (риск №1).
7. **Пять вопросов заказчику без явной блокировки кейса** (см. §4, вопросы 2/4/5/12/16) — кейсы
   001–006, 015, 032, 043–046, 092, 093, 111 написаны по предположению 04 без пометки «ждёт ответа»
   и будут требовать правки, если заказчик подтвердит другой вариант (например, вариант 03 по праву
   итога — см. §5 п.1).
8. **Статусная модель проверки может не материализоваться отдельно.** 04 §16 явно допускает, что
   вторая статусная модель (03 §8.3: Назначена/В работе/Проверена/Приостановлена/Отменена) не
   обязательна, если состояние проверки можно выразить локально в UI. Кейсы 067–069 пишут это как
   целевое API-поведение — при технической реализации через локальные UI-состояния эти 3 кейса
   потребуют переноса на UI-уровень или удаления.

## 7. Критерии готовности и приёмки; оценка объёма

### 7.1 Готовность этого плана

- Все 111 TC-P2P из `docs/test_cases/p2p/` учтены в матрице трассировки §3 ровно один раз (сверено
  построчно).
- Таблица §4 покрывает все 20 кейсов с пометкой «Ждёт ответа заказчика» из кейсов задачи A (вопросы
  1, 3, 6, 7, 8, 9, 10, 11, 13, 14, 15) и отдельно перечисляет 5 вопросов без прямой блокировки.
- Известные расхождения версий из README дополнены тремя новыми наблюдениями (§5).

### 7.2 Критерии приёмки функциональности (по «твёрдой» части 04/03, не зависящей от открытых
вопросов)

- Тумблер «Включить взаимопроверку» в карточке ПЗ: выключен → стандартный сценарий без изменений
  (001, 108); включён → доступен блок настроек (002).
- Штатные проверяющие ограничены существующим пулом «может быть проверяющим ПЗ» (003), назначение
  автоматически выдаёт роль «Преподаватель» (004).
- Слушателю-проверяющему собственная работа не назначается ни вручную, ни автоматически (022, 024).
- P2P работает только в рамках одного потока, участники — слушатели этого потока (015).
- Оба режима распределения (ручной/авто) реализованы и настраиваются независимо (016, 017).
- Ограничения ручного/авто распределения не действуют на внешнего проверяющего — ему выводится весь
  список сданных работ (025).
- До финального подтверждения peer-проверка редактируема, после — заблокирована (030, 031).
- Слушатель-проверяющий не может выставить итог и не может вернуть работу на доработку (032, 058).
- Итог выставляет и может менять только штатный проверяющий; администратор без назначения не может
  (044–046).
- Числовые критерии агрегируются средним с округлением до 0,1; текстовые — списком без агрегации
  (049, 050).
- Групповые ПЗ не могут быть переведены в режим взаимопроверки (097).
- Ограничение «одно ПЗ один раз в программе/потоке» не меняется P2P (111).
