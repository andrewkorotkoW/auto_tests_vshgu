# План автотестов: «Статистика обучения → Курсы»

Раздел админки `/admin/learning-statistics/courses` (карта по регионам + таблица курсов +
выгрузка). План читается без просмотра кода; пути к файлам даны только как справка, где
искать соответствующую логику.

**Важная оговорка.** В репозитории нет самого текста ПМИ/ДТТ по этому разделу — план
составлен по номерам и названиям блоков, которые дал владелец (Карта 1-9, Фильтрация
10-17, Таблица-столбцы 18, Таблица-прогресс 19-21, Выгрузка 22-25), и по факту того, что
реально работает на стенде develop. Состав столбцов таблицы (ДТТ п.3.2.2) и структура
xlsx-отчёта (ДТТ п.3.3.1) в репозитории не описаны — эти два пункта в плане явно помечены
«требует ручной сверки с ДТТ владельцем», гадать их не стали.

Уже готовая инфраструктура, на которую план опирается:
- `AdminDashboardPage` (открытие раздела курсов, поиск строки, чтение ячеек таблицы, готовые
  проверки строки курса по 5 столбцам — %, всего, не начато, в процессе, пройдено);
- `DashboardsEndpoint` (API-получение строки статистики курса с ожиданием, т.к. статистика
  считается асинхронно — без ожидания строка может быть ещё не рассчитана);
- `tests/ui/dashboards/conftest.py` и `test_admin_checks_program_and_course_dashboards.py`
  как образец: как готовится программа → поток → модуль → курс → слушатели, и как оформлен
  xfail на нестабильность develop;
- `tests/ui/courses/tincan/stream/test_user_tincan_flow.py` как образец прохождения курса
  слушателем — сейчас тоже xfail (не раскрывается шеврон модуля на странице курса), это риск
  для шагов 19-21, учтён в оценке ниже.

## Не автоматизируем и почему

- **Цвет региона на карте по пикселям/скриншоту.** Проверяем не визуально, а через
  DOM-атрибут/CSS-класс региона (например, `data-*`-атрибут интенсивности или имя класса
  цветовой градации), который меняется при пересчёте статистики. Скриншот-сравнение хрупкое
  к любому визуальному шуму (шрифты, антиалиасинг, версия браузера) и не даёт содержательной
  ошибки при падении.
- **«Время прохождения, мин» — точное совпадение.** Сравниваем с окном допуска ±N минут, а
  не посекундно, потому что между действием слушателя и пересчётом статистики есть
  задержка — тот же класс дефекта, что уже задокументирован как xfail в
  `test_admin_checks_program_and_course_dashboards` (поля passed/assignments_passed не
  обновились даже после 120с ожидания на develop). Точное совпадение будет давать ложные
  падения независимо от корректности функциональности.
- **Состав столбцов таблицы (ДТТ п.3.2.2) и структура xlsx-отчёта (ДТТ п.3.3.1).** Этих
  двух документов/описаний нет в репозитории. В план включены только те столбцы, что
  реально проверяются существующим кодом (`AdminDashboardPage.assert_course_row`: %,
  всего, не начато, в процессе, пройдено). Полный список столбцов и структуру отчёта нужно
  сверить вручную на стенде (`/admin/learning-statistics/courses` под администратором) —
  без этого дальнейшие шаги 18 и 24 гадать не стали.
- **Drill-down по клику на регион карты (шаг 8).** Поведение неочевидно ни из кода, ни из
  доступных описаний — тоже помечено «требует ручной сверки», чтобы не закладывать в тест
  придуманное поведение.

## Открытые вопросы для реализации (t2)

1. **Как регион слушателя связан с регионом на карте курса?** В `generate_user_payload`
   (`api/helpers/data_generator.py`) параметры `region_id`/`municipality_id` заданы жёстко
   (`region_id=1`, `municipality_id=158` по умолчанию) и не ссылаются на
   `settings.DEFAULT_REGION_ID`/`DEFAULT_MUNICIPALITY_ID` из `.env.example` — эти
   settings-значения (default 33 / 2310) сейчас нигде в коде не используются. При этом у
   модуля/элемента расписания (`generate_module_payload`, `generate_schedule_item_payload`)
   есть свой собственный `region_id`/`region_name` (default 33, «Москва»), а в
   `api/helpers/constants.py` есть отдельный список `CAS_LOCATIONS` — похоже, это
   подразделения/кафедры вуза, а не географические регионы. Неясно, какое из этих полей
   (region_id пользователя, регион модуля, CAS-локация) агрегируется картой курса — нужно
   выяснить у бэкенд-команды или подобрать эмпирически на develop перед тем, как писать
   шаги 5, 6, 9, 14.
2. **Фильтры по периоду и по региону (шаги 13-14) не реализованы в API-хелпере.**
   `DashboardsEndpoint.get_course_row`/`wait_for_course_row` сейчас поддерживают только
   `filters[name]`, `filters[type][]`, `filters[stream_id][]`. Для API-уровня проверок этих
   двух фильтров эндпоинт нужно расширять — объём доработки зависит от ответа на вопрос №1.
3. **`openpyxl` отсутствует в `requirements.txt`.** Без него нельзя программно читать
   содержимое xlsx-выгрузки (шаги 23-24). Нужно решение владельца — добавлять ли
   зависимость (это меняет requirements.txt, что выходит за рамки этой задачи).
4. **Риск: прохождение курса слушателем в UI сейчас xfail.**
   `test_user_tincan_flow.py` падает на developer-стенде из-за нераскрытого шеврона модуля
   (вкладки курса неактивны, пока модуль не развёрнут вручную) — это прямой риск для шагов
   19-21, которым нужно реальное прохождение курса слушателем в отдельном контексте
   браузера. Пока дефект не устранён (или не найден обходной локатор для разворачивания
   модуля), эти три шага либо остаются xfail, либо частично переносятся на API-уровень
   (`assignments_endpoint.change_state`) без реального прохождения в UI.
5. **Нестабильность стенда develop.** По опыту `tests/ui/dashboards` (xfail с 3
   зафиксированными прогонами: element not found при уже подтверждённой через API строке,
   обрыв соединения на POST /programs, один чистый прогон) — дашборды на develop
   нестабильны сами по себе, независимо от логики тестов. В оценку шагов 5, 6, 9, 19-21,
   24 стоит закладывать бюджет на повторные прогоны и вероятность xfail, а не рассчитывать
   на стабильный зелёный прогон с первого раза.
