Кейсы описывают целевое поведение по приоритетной версии (04 → 05, `docs/requirements/tz2026/README.md`).
Гистограммы по критериям одиночного/множественного выбора в отчёте — ручные кейсы (без автотеста).

**17.11.2026 — живая разведка на p2p-prototype (ПЗ «Разведка 07: усреднение (p2p)», content 192,
stream_content 61 в демо-потоке 31; две работы, 3 и 2 завершённые peer-проверки), подтверждено с
уточнениями:**
- **Реальный контракт агрегатов** — `GET /homework/{content_id}/answers/{homework_answer_id}/peer-results`
  (именованный маршрут `answers.peer-results`; это же XHR делает админская страница работы
  `/admin/homeworks/{content_id}/answer/{answer_id}`, см. `api/endpoints/p2p.py::get_peer_results`).
  Ответ `data.attributes`: `viewer` (`staff` | `author` | `peer_reviewer`), `reviews[]`
  (`peer_review_id`, `reviewer_name`, `review_score`, `values[]` по критериям), `reviews_count`,
  `review_score_avg`, `criteria_stats[]` — по каждому критерию `type`, `is_system`, `avg`,
  `entries[]` (значение/текст + `score` для choice-типов, `reviewer_type`/`reviewer_id`),
  `option_counts` (гистограмма по вариантам) и `options` для choice-типов. Черновики
  (`status=draft`) в `peer-results` НЕ попадают — только финализированные.
- **TC-P2P-049 опровергнут в части округления.** Среднее по количественному критерию считается,
  но округляется до ЦЕЛОГО, а не до 0,1: оценки 70/71/100 → `avg: 80` (80,33), оценки 70/71 →
  `avg: 71` (70,5 → округление вверх, не отбрасывание). Так же до целого округляются средний балл
  по choice-критерию (7/4 → 6 из 5,5), `review_score` каждой проверки (3,5 → 4; 6,5 → 7) и
  `review_score_avg` (4,5 → 5). UI («Среднее: 80», «Средний балл: 7») показывает те же целые.
- **TC-P2P-050 подтверждён**: качественный критерий — `avg: null`, `entries[].text` списком
  (UI: ссылка «N комментария», раскрывается список).
- **TC-P2P-051 подтверждён**: в одном ответе одновременно `avg` по числовым/choice и список
  текстов по качественным.
- **TC-P2P-052/053 подтверждены (ручные)**: `option_counts` = {id варианта: число выборов}; UI
  рисует под критерием список «Вариант: N» (Отлично 1 / Хорошо 1 / Слабо 1; Примеры 2 / Цитаты 2)
  плюс «Средний балл».
- **Формула `review_score` (балл одной проверки) восстановлена**: сумма `weight × score` по НЕ
  системным взвешенным критериям, округлённая до целого (0,5·7 + 0,5·3 = 5; 0,5·4 + 0,5·3 = 3,5 →
  4; 0,5·10 + 0,5·3 = 6,5 → 7). Системная «Общая оценка» (0–100) и качественные критерии в
  `review_score` НЕ входят. Балл multiple_choice при выборе двух вариантов по 3 балла = 3 (не 6) —
  среднее или максимум по выбранным, различить на равных баллах нельзя (критерии после первой
  проверки заморожены, `peer_criteria_frozen`) — открытый вопрос.
- **Настораживает (кандидат в дефект UI/формулы):** на странице работы штатного проверяющего
  блок «Оценка по взаимопроверке» показывает `review_score_avg` как «**5 из 100**», хотя
  максимум этой величины при весах 0,5/0,5 и баллах вариантов 10 и 3 — 6,5; значение не
  нормировано к 100. Либо подпись «из 100» ошибочна, либо формула должна нормировать баллы.
- Контракт сохранения критериев уточнён (01_criteria.md): у вариантов choice-критериев `id`
  ОБЯЗАТЕЛЕН и задаётся клиентом (`opt-<slug>-N`, иначе 422 «options.0.id обязательно»), у
  взвешиваемых критериев обязателен `weight` (422 «У взвешиваемого критерия нужен weight»).
- Видимость по ролям (задел для части 10): автор (`viewer: author`) при
  `author_see_peer_breakdown=false`/`author_see_reviewer_names=false` получает только
  `reviews[]` c `reviewer_name: null` без `values`, `reviews_count` и `review_score_avg`;
  слушатель-проверяющий (`viewer: peer_reviewer`) видит ВСЕ проверки по работе с именами и
  значениями — ответ на вопрос заказчика из 04 §3 (что видит проверяющий после отправки).
