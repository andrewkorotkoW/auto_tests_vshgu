# Тест-кейсы: 01. Конструктор критериев

| Параметр | Значение |
|---|---|
| Область | tests/api/p2p, tests/ui/p2p (форма критериев в карточке ПЗ) |
| Стенд | p2p-prototype (https://portal-p2p-prototype.d2.devspark.ru/) |
| Роли | admin |

Кейсы описывают целевое поведение по приоритетной версии (04 → 03, `docs/requirements/tz2026/README.md`).
Типы критериев и правила изменения формы — 03 §7 (04 §5 упоминает их кратко, без деталей по типам).
На этом этапе (кейсы до разработки) автотест не планируется — критерии не входят в перечень категорий
из миссии, отмеченных для автоматизации на Этапе 1.

**12.11.2026 — живая разведка (вкладка «Взаимопроверка» карточки ПЗ, p2p-prototype), подтверждено частично:**
- У каждого P2P-ПЗ есть один системный, неудаляемый критерий **«Общая оценка»** — тип «Количественный
  системный», шкала 0–100, его тип «изменить нельзя» (UI-подсказка), **не входит в сумму весов**
  остальных критериев. Ни один из TC-P2P-007…010 его не описывает — нужно завести отдельный кейс на
  системный критерий «Общая оценка» до работы с пользовательскими.
- Есть действие **«Применить набор по умолчанию»** — по клику форма критериев **заменяется набором по
  умолчанию и сохраняется сразу** (диалог-предупреждение: «Несохранённые правки критериев пропадут») —
  отвечает на вопрос №13 (TC-P2P-014): шаблон по умолчанию подтверждён как факт, его состав ещё не
  разведан (что именно входит, кроме системной «Общей оценки»).
- `peer_criteria_frozen` (bool) в ответе `/content` — похоже, это и есть флаг «критерии заморожены после
  первой проверки» из TC-P2P-011/012, но сам переход (когда именно он становится true) не разведан.

**12.11.2026, продолжение — реальный набор типов критериев подтверждён полностью (форма «+ Добавить
критерий» на вкладке «Взаимопроверка», /admin/activities/{id}), включая живой контракт API
(GET/POST `/homework/{id}/peer-criteria`, перехвачено через devtools):**
- **TC-P2P-007…010 опровергнуты по набору типов.** Реальный выпадающий список «Тип критерия» — ровно
  4 пункта: **Количественный** (`quantitative`), **Качественный** (`qualitative`), **Выбор одного
  варианта** (`single_choice`), **Выбор нескольких вариантов** (`multiple_choice`). Нет отдельного типа
  «Шкала» (количественный критерий и есть шкала, фиксированная 0–100 — своего диапазона у новых
  количественных критериев нет, те же 0–100, что у системной «Общей оценки»). Нет типа «Текстовое поле»
  — его роль играет «Качественный» (подсказка в UI: «Качественный критерий предполагает текстовую
  оценку или комментарий проверяющего. В сумму весов не входит.») — т.е. TC-P2P-010 по сути подтверждён,
  просто под другим именем типа.
  «Одиночный/Множественный выбор» (TC-P2P-008/009) подтверждены по сути: вариант ответа = подпись
  (`text`) + необязательный балл (`score`); подсказка в UI — «Баллы у вариантов необязательны. Вес
  критерия появится, когда хотя бы у одного варианта есть балл.».
- Подтверждён реальный контракт `GET /homework/{content_id}/peer-criteria` → `{"data": [{id, type,
  title, sort_order, score_min, score_max, weight, options, is_system}]}`. Системная «Общая оценка»:
  `type=quantitative, score_min=0, score_max=100, weight=null, is_system=true`. Пользовательские
  критерии: `qualitative` — без score_min/max/weight/options; `single_choice`/`multiple_choice` —
  `options: [{id: "opt-...", text, score}]`, `weight` — доля от 0 до 1.
- Подтверждён механизм веса: сумма весов всех НЕ системных критериев = 1, распределяется АВТОМАТИЧЕСКИ
  поровну между критериями, у которых есть хотя бы один оценённый вариант/число (кнопка «Распределить
  поровну» в UI). Критерий с весом можно видеть и менять вручную (поле «Вес критерия (от 0 до 1)»),
  сумма пересчитывается.
- Сохранение формы критериев — кнопка «Сохранить» на вкладке «Взаимопроверка» → реальный запрос
  `POST /homework/{content_id}/peer-criteria` (подтверждён путь/метод; точное тело запроса не
  перехвачено напрямую, инференс — полная форма как в ответе GET, см.
  `api/endpoints/p2p.py::set_criteria`).
- Техническая находка (автоматизация): выпадающий список «Тип критерия» (Vuetify-комбобокс) часто не
  рендерит видимое меню после первого клика — нужен ОДИН лишний `key: "Down"` после клика, чтобы меню
  отрисовалось непрозрачным и опции стали кликабельны по координатам; без этого элементы в DOM есть, но
  их bounding box нулевой (клик по ref проваливается с «entirely outside the viewport»). Похоже на
  мелкий баг рендеринга в самом продукте (не специфично для автоматизации — наблюдалось и при ручном
  использовании через интерактивный браузер).
