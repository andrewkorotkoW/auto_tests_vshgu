**12.11.2026 — ветка появилась, начата живая разведка (стенд p2p-prototype).** Ниже сведено с
реальным контрактом то, что проверено; остальные кейсы файла по-прежнему написаны по приоритетной
версии требований (04 → 03 → 02) и не подтверждены — сверка продолжается по частям, как с МТС Линк.

**Подтверждено живьём (admin, `POST /content` + карточка активности в `/admin/activities/{id}`):**
- Тумблер называется в реальном UI **«Взаимопроверка»** (не «Включить взаимопроверку») и реально
  задаётся полем `peer_review_enabled` (bool) **прямо в payload создания** `POST /content` — отдельного
  PATCH/endpoint на включение нет (контраст с `P2PEndpoint.enable_peer_review`, которая предполагала
  `PATCH /content/{id}/peer-review` — это неверно, нужно чинить при своде `api/endpoints/p2p.py`).
- **TC-P2P-002 опровергнут в своей предпосылке:** тумблер нельзя переключить ПОСЛЕ создания карточки —
  ни в UI (поле видимо, но задизейблено даже в режиме «Редактировать», подпись прямо гласит
  «Выбирается при создании карточки и после сохранения не меняется»), ни что-либо предполагает обратное
  через API. «Включение тумблера открывает блок настроек» в реальности происходит только при
  **создании** ПЗ с `peer_review_enabled: true` — после сохранения появляется отдельная вкладка
  карточки «Взаимопроверка» (не инлайн-блок на «Общей информации»).
- **Новое ограничение, которого не было в плане:** «Для групповых ответов взаимопроверка недоступна» —
  нужно завести отдельный негативный кейс (создание P2P-ПЗ с групповым ответом должно быть
  заблокировано/недоступно).
- На вкладке «Взаимопроверка» карточки, помимо тумблера, лежат ещё два реальных блока:
  **«Внешняя проверка»** (`external_review_allowed`, bool) — ОТДЕЛЬНЫЙ тумблер, в отличие от
  `peer_review_enabled` остаётся редактируемым после создания (пока не «заблокирован» — см.
  `external_review_config_locked` в ответе `/content`, условие блокировки ещё не разведано, кандидат
  на `05_external_reviewer.md`); и **«Критерии оценки»** — конструктор критериев, см. `01_criteria.md`.
  «Штатных проверяющих» и формы «кто допущен быть проверяющим» на этой вкладке НЕТ — по тексту
  подсказки «Внешняя проверка… ссылки создаются в потоке» это, похоже, настройка уровня **потока**, а
  не карточки — TC-P2P-003/004/005 (штатные проверяющие в карточке) нужно переразведать на вкладке
  потока (`02_stream_settings.md`), не здесь.
- Подтверждённые поля ответа `GET/POST /content` для ПЗ: `peer_review_enabled`, `external_review_allowed`,
  `external_review_config_locked`, `peer_criteria_frozen` (замороженность критериев — видимо то самое
  ограничение из TC-P2P-011/012), `peer_pass_threshold` (порог прохождения, ещё не разведан — кандидат
  на `06_final_result.md`/`09_statuses.md`).
- Важно: **все поля — плоские, прямо в `data.attributes`**, никакого отдельного объекта `meta` в ответе
  НЕТ — если в тест-кейсе или плане встретится формулировка «флаги в meta», это неверная предпосылка.

**13.11.2026 — живая разведка `peer_pass_threshold` (действие «Включить взаимопроверку на карточке
ПЗ» + порог зачёт/незачёт при `grade_type=pass_fail`), подтверждено живьём (API, `POST`/`PUT /content`):**
- `peer_pass_threshold` присутствует в ответе ВСЕГДА (не только при `pass_fail`), но его значение
  зависит от `grade_type`: при `grade_type=pass_fail` — число (по умолчанию `50`, если явно не задать
  своё значение в payload создания — пробовали `75`, принялось); при `grade_type=five_point` (и,
  предположительно, `ten_point`) — `null`. Похоже на процентный порог для автоматического перевода
  агрегированной peer-оценки в «зачёт»/«незачёт», но сама логика применения (на каком этапе и как
  считается итог) ещё не прослежена до конца — см. `06_final_result.md`.
- **`peer_pass_threshold` РЕДАКТИРУЕМ после создания карточки** (в отличие от `peer_review_enabled`) —
  `PUT /content/{id}` с новым значением в `data.attributes.peer_pass_threshold` сработал (75→90).
- **`peer_review_enabled` подтверждён неизменяемым и на уровне сервера, не только UI**: `PUT
  /content/{id}` с другим значением `peer_review_enabled` отдаёт 422 с точным текстом «Нельзя изменить
  признак включения взаимопроверки после создания карточки.» — то есть это не просто задизейбленное
  поле в форме редактирования (ранее было подтверждено только через UI), а серверная валидация.
- Попутно: `PUT /content/{id}` отклоняет `external_review_config_locked`/`peer_criteria_frozen` в теле
  запроса 422-ошибкой «должно отсутствовать» — это read-only/вычисляемые сервером поля, в payload
  обновления их слать нельзя вообще (не только не менять значение, а не включать ключ).

Спорные точки — с предусловием `Ждёт ответа заказчика: вопрос №N (05_вопросы_заказчику_16)`.
