Кейсы описывают целевое поведение по приоритетной версии (04 → 02, `docs/requirements/tz2026/README.md`).
Вид автора не входит в перечень категорий Этапа 1, отмеченных для автоматизации, — автотест не планируется.

**17.11.2026 — живая разведка на p2p-prototype (работы 46/47 content 192, демо-работа 29 content 158),
подтверждено, ответы на вопросы заказчика из 04 §3 получены из реального поведения:**
- **Где автор видит результат**: в ТОЙ ЖЕ панели деталей ПЗ (вкладка «Курсы и тесты» → карточка ПЗ),
  под своим ответом и блоком «Назначенные взаимопроверки» появляется блок **«Взаимопроверка»**:
  «Завершённых проверок N (слушателей N, внешних M)», «Оценка по взаимопроверке N из 100»,
  «Значения по критериям» (по каждому критерию: тип-чип, «Среднее»/«Средний балл» + список
  «Вариант: N» для choice-типов, для качественного — ссылка «N комментария» или «—»), список
  **«Проверки»** (раскрывающиеся строки «<проверяющий> · Слушатель · Оценка: N»). Данные —
  `GET /homework/{content}/answers/{answer}/peer-results` с `viewer: "author"` (тот же эндпоинт,
  что у штатного проверяющего, ответ урезан по author_visibility). Панель грузится долго
  (15–20 с до появления блока — спиннер), при каждом открытии фронт дополнительно дёргает
  `GET /my/homework-answers/{answer}/peer-review-report` → 422 «Отчёт ещё не сформирован» и пишет в
  консоль «Server communication error» (см. 11_report.md).
- **TC-P2P-071 подтверждён**: статус в шапке панели — «На проверке» (on_review, с «История
  изменений»), «Возвращено на доработку после проверки» (sent_back, + «Редактировать»),
  «Проверено» + зелёный бейдж оценки (accepted). Peer-статусов нет (09_statuses.md).
- **TC-P2P-072 подтверждён**: после итога — один бейдж оценки (например «5») рядом со статусом
  «Проверено»; «Оценка по взаимопроверке» показывается отдельно и в итог не подменяется.
- **TC-P2P-073 уточнён**: значения по критериям автор видит НЕ только после итога, а сразу по мере
  финализации peer-проверок (на работе 47 в статусе «На проверке» уже виден блок с 1 проверкой) —
  при `author_visibility.author_see_peer_breakdown=true`.
- **TC-P2P-074 решён настройкой потока** `author_visibility.author_see_peer_breakdown`
  (02_stream_settings.md): `false` → API отдаёт только `reviews[]` (id без значений),
  `reviews_count`, `review_score_avg` (в UI — только счётчик и оценка); `true` → добавляются
  `values` в каждой проверке и `criteria_stats` (агрегаты + отдельные проверки одновременно).
- **TC-P2P-075 решён настройками** `author_see_reviewer_names` (false → `reviewer_name: null`, в UI
  строка «Проверяющий 1», «Проверяющий 2»…) и `author_see_comments` (false → значение
  качественного критерия `null`, в UI «—» вместо «N комментария»). Все три флага редактируются
  и после `frozen` (меняются сразу, без переподключения).
- **TC-P2P-076 подтверждён по API**: слушатель-проверяющий после своей проверки получает
  `viewer: "peer_reviewer"` с ПОЛНЫМ списком всех проверок по этой работе — с именами проверяющих,
  баллами и значениями по критериям (без `reviews_count`/`review_score_avg`/`criteria_stats`);
  посторонний слушатель (без назначения) — 403. UI-представление для проверяющего не снималось.
