Кейсы описывают целевое поведение по приоритетной версии (04 → 03, `docs/requirements/tz2026/README.md`).
Известное расхождение версий (README): право итогового результата — 04: любой штатный проверяющий
ПЗ; 03: отдельный признак «Может выставлять итоговый результат»; 02: верификация преподавателем.
Кейсы 043–046 написаны по приоритетной версии 04 (без отдельного признака).

**13.11.2026 — живая разведка `peer_pass_threshold` (карточка ПЗ, см. 00_pt_card_settings.md),
подтверждено частично:** поле `peer_pass_threshold` (`data.attributes` ответа `/content`, число,
только при `grade_type=pass_fail`, по умолчанию `50`, редактируемо после создания через `PUT
/content/{id}`) — похоже на процентный порог для автоматического «зачёт»/«незачёт» по агрегированной
peer-оценке, но сама логика применения (когда и как именно он используется при подведении итога, как
соотносится с `auto_final_grade_enabled` из `peer_settings` потока — 02_stream_settings.md) НЕ
прослежена до конца — работу через полный цикл с `pass_fail` + реальным набором peer-проверок ещё не
проводили.

**13.11.2026 — подтверждено владельцем вручную на p2p-prototype (не автотестом/скриптом, живая
проверка в UI):** штатный проверяющий (он же преподаватель/админ) может выставить обычную оценку
ПЗ, и она отображается **ВМЕСТЕ** с результатами взаимопроверки, а не вместо них. Это подтверждает
ключевую предпосылку приоритетной версии 04 — штатная проверка остаётся независимым решающим
звеном, peer-оценки её не подменяют (см. `04_версия_после_встречи_с_заказчиком.md:118-122`,
процитировано в обсуждении части 06). Детали механики (что именно видно рядом — агрегаты по
критериям, какой из двух результатов считается «итоговым» для статуса работы, не путается ли это с
`peer_pass_threshold` при `grade_type=pass_fail`) — пока не разведаны пошагово через API/UI-контракт,
зафиксирован только сам факт сосуществования.

**17.11.2026 — живая разведка на p2p-prototype (content 192 / работа 46, демо-поток 31), подтверждено
с уточнениями:**
- **Отдельного эндпоинта «итоговый результат» нет** — в таблице именованных маршрутов стенда
  (`/routes`, см. `_routes_p2p-prototype.md`) нет ни `final-result`, ни `peer-reviews` на
  `/homework/{id}`; каркас `set_final_result`/`get_aggregates`/`get_peer_reviews_for_work` был
  неверной догадкой. Итог выставляется ШТАТНЫМ механизмом проверки ПЗ: `POST /homework/{content_id}/
  answers/{answer_id}/examination` `{"data":{"attributes":{"grade","status":"accepted","deadline",
  "teacher_comment"}}}` (`api/endpoints/homework.py::examine`), peer-проверки читаются из
  `GET .../answers/{answer_id}/peer-results` (07_aggregation.md).
- **TC-P2P-043 подтверждён**: админская страница работы (`/admin/homeworks/{content}/answer/{answer}`)
  делает три XHR — `answers/{id}`, `peer-criteria`, `peer-results` — и показывает блок
  «Взаимопроверка»: «Завершённых проверок N (слушателей N, внешних M)», «Оценка по взаимопроверке»,
  «Агрегированные значения по критериям», «Полученные проверки» (раскрывающиеся строки
  «ФИО · Слушатель · Оценка: N»), кнопка «Пересобрать отчёт (PDF)»; ниже — обычное поле «Оценка»
  и «Отправить».
- **TC-P2P-044 подтверждён с уточнением статуса**: после examination `grade=4`,
  `answer_status: accepted`, `status: 2`; отдельного статуса «Итоговый результат выставлен» НЕТ —
  переиспользуется «Принято» (04 §10 допускает). В `history` появляется запись `accepted` с
  `is_auto_final: false`.
- **TC-P2P-045 подтверждён**: повторный examination с другой оценкой проходит (4 → 5), peer-агрегаты
  при этом не меняются (`reviews_count`/`review_score_avg` те же).
- **TC-P2P-046 опровергнут на этой ветке**: администратор `admin3` (роли admin + teacher), НЕ входящий
  в список `teachers` работы (там только id 16), успешно выставил и изменил итог по работе 30
  (examination 200). Право выставлять итог определяется штатными правами проверки ПЗ
  (`can-check-homework-answers`), а не «назначением проверяющим ПЗ» из 04 §3/§9. Кейс оставлен
  как расхождение с требованием — решение за владельцем/заказчиком.
- **Новое правило (важно для 08/09)**: после выставления итога (`accepted`) взаимопроверка по работе
  ЗАКРЫВАЕТСЯ: ручное назначение нового проверяющего ещё проходит (201), но у него список
  `peer-submissions` пуст, а finalize даёт 422 «Работа на доработке или уже принята: …». То же
  правило действует и для работ, принятых ДО назначения (проверено на демо-работе 29).
- Итог НЕ выставляется автоматически по достижении `min_reviews_per_work` (3 проверки при M=3 —
  работа осталась `on_review`, `grade: null`). Флаг `auto_final_grade_enabled` через
  `PUT .../peer-settings` на ПЗ с `grade_type=five_point` отклоняется 422 «Поле peer settings.auto
  final grade enabled должно отсутствовать» — где и для какого типа оценки он включается, не
  найдено (вероятно, только `pass_fail` + `peer_pass_threshold`, см. 00_pt_card_settings.md);
  TC-P2P-047 остаётся открытым.
- TC-P2P-048: итог выставляется в любой момент после сдачи — проверено на работе 30 вообще без
  peer-проверок (`reviews_count: 0`) — ограничения «после минимума проверок / срока» нет.
- Отчёт автора `GET /my/homework-answers/{answer_id}/peer-review-report` сразу после проверок →
  422 «Отчёт ещё не сформирован» (асинхронная сборка, как у отчёта потока в 03_distribution.md);
  чужой пользователь → 403.
