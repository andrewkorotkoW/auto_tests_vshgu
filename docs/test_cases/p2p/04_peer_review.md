Кейсы описывают целевое поведение по приоритетной версии (04 → 03, `docs/requirements/tz2026/README.md`).
Разведка селекторов — `ui/pages/practical_task_page.py`, `ui/pages/reviewer_page.py`
(`tests/ui/practical_tasks/test_review_practical_task.py`) — образец структуры, не менялись.

**12.11.2026 — живая разведка (панель деталей ПЗ, p2p-prototype), подтверждено частично
(без assign/distribute — запись намеренно не вызывалась):**
- **TC-P2P-028 опровергнут частично**: нет отдельной вкладки/раздела «Работы на проверку».
  Реальность: блок «Назначенные взаимопроверки» встроен ПРЯМО в панель деталей ПЗ — та же
  панель, где слушатель сдаёт собственный ответ (под формой «Ваш комментарий»/«Прикрепить
  файл»). Блок виден любому слушателю потока, независимо от того, есть ли у него назначения.
- Подтверждено пустое состояние: заголовок «Назначенные взаимопроверки», счётчик «Назначено
  работ: 0», текст-заглушка «Вам пока не назначены работы для проверки.».
- Попутно подтверждён и исправлен контракт `GET /homework/answers?filters[homework_id]=`:
  реальная структура — `attributes.user.id` (вложенный объект), а не плоский `attributes.
  user_id`, как предполагал `_find_work_id` в tests/ui/p2p/test_peer_review.py.
- Попутно подтверждена и исправлена фикстура `p2p_practical_task` (tests/ui/p2p/conftest.py):
  она звала несуществующий `p2p_endpoint.enable_peer_review` (PATCH) после создания ПЗ вместо
  передачи `peer_review_enabled=True` в payload создания (см. 00_pt_card_settings.md).

**12.11.2026, продолжение — владелец подтвердил запись на тестовых данных, часть доведена до конца:**
- Подтверждён реальный контракт `assign_work_manually`: `POST .../contents/{stream_content_id}/
  peer-assignments`, тело ПЛОСКОЕ (без JSON:API-обёртки) — `{"author_user_id", "reviewer_user_id"}`
  (не `work_id`, как предполагалось). Ответ: `homework_peer_assignment_id`,
  `stream_module_content_id`, `content_id`, `reviewer_user_id`, `author_user_id`,
  `homework_answer_id`, вложенные `reviewer`/`author`/`homework_answer` объекты.
- Подтверждён реальный контракт `save_peer_settings`: `PUT .../peer-settings`, тело тоже
  ПЛОСКОЕ — `{"peer_settings": {...}}` — и это ПОЛНАЯ замена (сервер требует разом
  min_reviews_per_work/reviews_per_reviewer/peer_review_deadline_at/author_visibility.*/
  external_see_author_names, без них 422; external_cert_reviews_threshold(_max)/
  auto_final_grade_enabled/frozen — необязательны).
- `run_automatic_distribution` (`PUT .../peer-assignments/distribute`) — путь неверный: сервер
  трактует «distribute» как `{assignment_id}` route-binding (500 "invalid input syntax for type
  bigint: distribute"), то есть под `/peer-assignments/{id}` живёт PUT/PATCH/DELETE отдельного
  НАЗНАЧЕНИЯ, а не массовое авто-распределение — реальный путь автораспределения **всё ещё не
  найден** (кнопка «Распределить» в модалке не нажималась на предыдущем заходе; это отдельный
  эндпоинт, не предполагавшийся `/distribute`).
- **TC-P2P-028/029 подтверждены другим, более точным контрактом**, чем предполагал каркас:
  реальный список «чужих работ» и форма проверки живут не под числовым `/programs/{id}`
  (админская схема), а под `/my-programs/{program_uuid}` (тот же UUID, что в адресной строке
  слушателя) — РАЗНЫЕ id-схемы для одной программы. Подтверждено:
  `GET /my-programs/{uuid}/modules/{module_id}/contents/{stream_content_id}/peer-submissions`
  → список `{homework_answer_id, title, author_name, submitted_at, my_review_status,
  revision_status, peer_review_allowed}` — UI-таблица «Назначенные взаимопроверки» рендерит
  колонки «Работа»(=author_name, простая строка, не объект)/«Сдана»(=submitted_at)/«Статус»
  (="Не оценена" при my_review_status=null) + кнопку «Перейти к проверке», а над таблицей —
  чипы «Доступны работы»/«Назначено работ: N» и прогресс «Проверено: M из N».
  `GET .../peer-submissions/{homework_answer_id}` → детали + `criteria` (список критериев для
  формы; пусто, если на ПЗ критерии не настраивались — тогда форма «Оценка» показывает только
  кнопки без полей, это не баг, а следствие пустого списка критериев) + `review`/
  `revision_status`.
- **TC-P2P-031 уточнён/опровергнут частично**: блокировка после «Завершить оценку» —
  подтверждённый диалог-предупреждение гласит «После завершения оценку нельзя будет изменить,
  **пока автор не сдаст работу заново**» — то есть блокировка УСЛОВНАЯ (до пересдачи автором), а
  не постоянная, как предполагал кейс.
- Подтверждён реальный контракт финализации: `POST .../homework/answers/{homework_answer_id}/
  peer-reviews/finalize`, тело — ВНОВЬ в JSON:API-обёртке (в отличие от flat-тел выше!):
  `{"data": {"attributes": {"values": {...}}}}`, `values` обязательно. Точная форма `values`
  (критерий→значение) НЕ подтверждена до конца — на тестовых данных этого захода `criteria=[]`
  (ПЗ без настроенных критериев), запрос стабильно получал 422 независимо от содержимого.
  «Сохранить черновик» (TC-P2P-030, промежуточное сохранение без финализации) остаётся НЕ
  подтверждён — кнопка была задизейблена при пустых критериях, реальный запрос не перехвачен.
  Следующий шаг: завести ПЗ с реальными критериями (через UI «+ Добавить критерий», раз API
  `set_criteria` тоже не подтверждён) и повторить полный цикл TC-P2P-029/030/031 с непустой
  формой.
- Техническая находка (для будущей разведки): `page.locator("body").inner_text()` на этом
  приложении почти всегда возвращает только «Назад» независимо от реального содержимого панели
  — страница явно рендерит контент не в обычном потоке body (Vue teleport/портал или подобное).
  Скриншоты надёжнее текстового дампа для проверки состояния этой конкретной страницы.
