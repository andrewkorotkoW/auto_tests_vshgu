02.11.2026: сведено с реальным контрактом (живая разведка на mts-link-release-main). Реальный путь
загрузки — `POST /upload/schedule_item_files` (не `.../schedule-items/{id}/files`, которого нет) +
отдельный ПОЛНЫЙ PUT элемента расписания, чтобы добавить загруженный материал в `attributes.files`. У
привязанных файлов нет индивидуального статуса привязки — только метаданные материала (имя/размер/
url) плюс агрегированный `files_sync_status`; проверки TC-MTS-036…038 теперь смотрят на присутствие
файла по имени в `attributes.files`, а не на выдуманный флаг «attached». TC-MTS-040/041 удалены:
первый требовал аудит-лога запросов (`request_log_audit`, подтверждённо не существует, 404) — и
вдобавок реальный эндпоинт загрузки принимает `files[]` пачкой, а не по одному файлу, так что сама
посылка «по одному за раз» под вопросом; второй требовал управляемой ошибки от МТС Линк, которой
никогда не было (нет мока). TC-MTS-039 переименован в `test_invalid_file_rejected_before_upload` и
сужен до одной проверки — что клиентская валидация формата/размера не даёт отправить файл вовсе
(сценарий «второй файл всё равно загрузится» убран вместе с нём, т.к. зависел от выдуманной
детализации по файлу). Детали — docs/test_cases/mts_link/16_prod_safe_run.md.
