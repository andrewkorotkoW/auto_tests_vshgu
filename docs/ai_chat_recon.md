# Разведка: контракт API и селекторы «Чат с ИИ в курсах»

Снято 07.10.2026 на `--env develop` (`https://portal-develop.d2.devspark.ru`), `HEADLESS=1`, реальным
перехватом сетевых запросов (Playwright `page.on("request"/"response"/"websocket")`) в одноразовых
скриптах (не сохранены в репозитории). Все активити/пользователи, созданные для разведки, удалены
после каждого шага через `TincanEndpoint.mass_delete` / `UsersEndpoint.delete`, кроме одного случая —
см. раздел «Незакрытый артефакт разведки» ниже.

Контракт в `docs/plans/2026-10-07_ai_chat_pmi_mission.md` совпал почти везде; расхождения отмечены
явно (**уточнено**/**не подтвердилось**).

## 1. Контракт API — админка

### 1.1 Карточка активити, вкладка «Чат с ИИ»

- `GET /admin/activities/{id}?i=1` открывает карточку сразу на вкладке «Чат с ИИ» (`i=1` — индекс
  вкладки; `i=0`/без параметра — «Общая информация»). Подтверждено: при заходе по `?i=1` блок
  `activity-details-ai-chat-settings` уже отрендерен в DOM без дополнительного клика по вкладке.
- `GET /content/{id}/llm-chat` у новой активити → `{"data": null}`. Подтверждено точно.

### 1.2 Включение переключателя и первая загрузка файла

- Клик по переключателю **не вызывает никакого запроса** — флаг только локальный (Vue state), пока
  не загружен первый файл. Подтверждено: после клика в транскрипте 0 новых запросов, был только
  предыдущий `GET /content/{id}/llm-chat`.
- `POST /upload/llm_knowledge_files` (multipart, поле файла — **`files[]`**, не `files` и не `file`;
  без этого backend отвечает 422 `"Поле files обязательно для заполнения."`) →
  ```json
  {"data":[{"uuid":"<storage_uuid>","attributes":{"name":"soups.docx","type":"application/vnd.openxmlformats-officedocument.wordprocessingml.document","size":227916,"url":"https://.../static/content/<storage_uuid>/soups.docx","created_at":"...","update_at":"..."}}]}
  ```
  Файлы с одинаковым содержимым дедуплицируются по хэшу — повторная загрузка того же файла возвращает
  **тот же `uuid`**, даже для другой активити (см. дефект в разделе 4).
- `POST /content/{id}/llm-chat` body `{"files": ["<storage_uuid>"], "is_enabled": 1}` → 201:
  ```json
  {"data":{"id":2,"llm_knowledge_uuid":"<uuid>","is_enabled":true,
    "knowledge":{"llm_knowledge_uuid":"<uuid>","user_id":3,"knowledge_name":"<имя активити>",
      "created_at":"...","updated_at":"...",
      "meta":{"files":{"<file_uuid>":{"llm_storage_uuid":"<storage_uuid>","status":"pending"}}},
      "files":{"<storage_uuid>":"soups.docx"},"status":"pending","user":"<ФИО админа>"},
    "questions_count":0,"answers_count":0,"created_at":"...","updated_at":"..."}}
  ```
  Это `data.id` (целое, в примере `2`) — отдельный числовой id записи `llm-chat`, отличный от
  `llm_knowledge_uuid`; именно он используется в контракте слушателя (`POST /llm-chat/{id}`, раздел 2).
- Обработка: опрос `GET /content/{id}/llm-chat` — `knowledge.meta.files[*].status` идёт
  `pending → completed | empty_context`. Наблюдаемое время обработки — от ~15 с до ~40 с на файл
  (один раз пришлось ждать дольше, см. раздел 4). `knowledge.status` = `completed`, только если
  **все** файлы `completed`, иначе `failed` (один `empty_context`-файл валит общий статус — подтверждено
  точно, как и было в плане).

### 1.3 Добавление второго файла

- `POST /upload/llm_knowledge_files` (то же, новый файл).
- **`PATCH /llm-knowledge/{llm_knowledge_uuid}/files`** body `{"files": ["<storage_uuid>"], "operation": "add"}`
  → 200 `{"data":{"status":"success"}}`. Это тот же эндпойнт, что и для удаления (см. 1.4) — различается
  только `operation`.

### 1.4 Удаление файла корзиной — **точный контракт снят**

Диалог подтверждения: модалка `.base-modal` с заголовком «Удаление файла», текстом
`Удалить файл «<имя файла>» из контекста обсуждения?`, кнопками `.confirm__btn-cancel` («Отмена») и
`.confirm__btn-ok` («Удалить», класс `error`).

После подтверждения:
```
PATCH /llm-knowledge/{llm_knowledge_uuid}/files
{"files": ["<storage_uuid>"], "operation": "remove"}
→ 200 {"data":{"status":"success"}}
```
за которым фронт сразу перечитывает `GET /content/{id}/llm-chat` (файл пропадает из `knowledge.files`
и `knowledge.meta.files`). **Важно**: тело использует `llm_storage_uuid` (ключ из `knowledge.files`),
а не вложенный `file_uuid` (ключ `knowledge.meta.files`) и не numeric id.

Эндпойнт `/llm-knowledge/{uuid}/files` (оба `operation`) и `/activities/mass-delete` возвращают
**423** с телом `{"data":{"status":"Коллекция заблокирована до окончания обработки контекста"}}`,
пока хотя бы один файл знания в статусе `pending` — см. дефект в разделе 4. `PATCH /content/{id}/llm-chat`
(выключение) и `GET /content/{id}/llm-chat/export` этой блокировкой **не затронуты** (отвечают 200
даже при `pending`-файле) — подтверждено точно.

### 1.5 Выключение переключателя

`PATCH /content/{id}/llm-chat` с пустым телом → 200 `{"data":{"status":"success"}}`, после чего
`GET /content/{id}/llm-chat` → `is_enabled: false`. Подтверждено точно, как в плане.

### 1.6 Скачать историю

`GET /content/{id}/llm-chat/export` → 200 `{"data":{"status":"success"}}`. Подтверждено точно
(файл формируется асинхронно, содержимое не проверяется — по плану).

### 1.7 Фильтр «Курсы с чатом ИИ» — **имя уточнено**

Реальный запрос фронта при включении галочки и клике «Применить»:
```
GET /activities?per-page=25&page=1&filters[name]=<поиск>&filters[is_llm_chat_enabled]=1
```
**Это НЕ `filters[llm_chat]=1`, как предполагалось в плане** — правильное имя параметра
**`filters[is_llm_chat_enabled]`** (совпадает с полем активити `is_llm_chat_enabled` из плана).

### 1.8 Значок «Чат с ИИ» в таблице активити

В ячейке типа сущности (`<span>курс Tincan</span>`) рядом с текстом типа появляется SVG-иконка
(речевой пузырь с тремя точками, `path="M20 2H4C2.9 2 2 2.9 2 4V22L6 18H20C21.1 18 22 17.1 22 16V4C22 2.9 21.1 2 20 2M20 16H5.2L4 17.2V4H20V16M17 11H15V9H17M13 11H11V9H13M9 11H7V9H9"`).
Иконка появилась сразу после `is_enabled: true` (даже пока файл ещё `pending`) — подтверждает факт
плана «значок привязан к переключателю, а не к документам».

## 2. Контракт API — слушатель, чат в плеере

### 2.1 Кнопка чата и открытие панели

Кнопка `button.player-chat-toggle` рендерится **в самом плеере (внешняя страница, не внутри
`#iframe` с содержимым xAPI)** — появляется независимо от того, загрузился ли сам SCORM/xAPI-пакет
внутри iframe. Открытие чата не вызывает отдельного REST-запроса — панель (`aside.player-chat`) уже
присутствует в DOM (просто `hidden`/без класса `_opened`), данные для подключения (`data-launch-key`,
`data-ws-endpoint`, `data-ws-token`) отрисованы на сервере вместе со страницей плеера.

### 2.2 Вопрос

```
POST /llm-chat/{numeric_llm_chat_id}
{"message": "Из чего варят гороховый суп?"}
→ 200 {"message":"Генерация установлена в очередь","llm_answer_id":12}
```
`{numeric_llm_chat_id}` — это `data.id` из `GET /content/{id}/llm-chat` (в примере — `11`), **не**
`llm_knowledge_uuid` и не `content_id` самой активити.

### 2.3 Ожидание ответа — два параллельных механизма

1. **Поллинг**: `GET /llm-chat/{numeric_llm_chat_id}?per-page=50` → пагинированная история:
   ```json
   {"data":[{"llm_answer_id":12,"request":"Из чего варят гороховый суп?","answer":[],
             "created_at":"...","updated_at":"...","status":"pending"}], "links":{...}, "meta":{...}}
   ```
   после готовности ответа — `status: "completed"`, `answer: ["Гороховый суп варят из кофчёных рёбер, гороха, картофеля и ..."]`.
2. **WebSocket (Centrifugo)**: `GET /ws-config` → `{"token":"<JWT>","expired":<unix>,"wsEndpoint":"wss://.../connection/websocket"}`.
   Подключение `wss://portal-develop.d2.devspark.ru/connection/websocket`, Centrifugo-протокол
   (`{"connect":{"token":"<JWT>","name":"client-frontend"},"id":1}`), подписка на канал
   `listener#{user_id}` приходит в ack подключения. Готовый ответ приходит пушем:
   ```json
   {"push":{"channel":"listener#5711","pub":{"data":{
     "status":"completed","timestamp":1791403771,
     "payload":{"id":10,"entity_type":"LMSCore\\Infrastructure\\Content\\Db\\Eloquent\\Content",
       "entity_id":7466,"question":"Из чего варят гороховый суп?",
       "answer":["К сожалению, моих знаний недостаточно, чтобы ответить на Ваш вопрос."],
       "status":"completed"}},"offset":1,"epoch":"..."}}}
   ```
   (в этом конкретном прогоне ответ получился отказом — соусы.pdf тогда ещё не был в контексте этой
   активити; на другом прогоне с реальным контекстом ответ по теме пришёл так же быстро через оба
   канала).

**Время ответа**: во всех прогонах разведки (3 вопроса, разные активити/контексты) ответ появлялся
в интерфейсе через **~5 секунд** — значительно быстрее отведённого в плане таймаута 120 с. Таймаут
120 с в будущих тестах остаётся как защита от выбросов, а не ожидаемое типичное время.

Поле ввода (`textarea.player-chat__input`) не содержит явного `disabled`-атрибута во время ожидания
в HTML-дампе — проверить блокировку поля и подпись «ИИ помощник печатает…» позже отдельным снимком
DOM в момент ответа (в разведке подтверждено только появление сообщений в `.player-chat__body`,
сам момент «печатает» не зафиксирован из-за быстрого ответа — 5 с против интервала опроса DOM 5 с).

### 2.4 Оценка (звёзды + комментарий)

```
POST /ratings
{"data":{"attributes":{"rating":4,"entity_type":"llm_chat","entity_id":11,"body":"\nАвтотест: разведка оценки чата"}}}
```
`entity_id` — тот же числовой `llm-chat` id, что в п. 2.2 (не `llm_answer_id`, не uuid). Эндпойнт
`/ratings` — общий (не специфичный для ИИ-чата) механизм оценок платформы.

## 4. Кандидаты в дефекты, найденные в разведке

1. **Повторная загрузка файла с уже известным по хэшу содержимым навсегда остаётся в статусе
   `pending` у новой активити — блокирует удаление файла и удаление самой активити (423 бессрочно).**
   Воспроизведено: активити 7458 (первая загрузка `soups.docx`, обработка ~15 с → `completed` →
   удалена успешно) → активити 7460 (повторная загрузка **того же файла**, backend вернул тот же
   `storage_uuid`, что и для 7458) — статус знания остался `pending` **более 50 минут** (проверено
   многократным опросом с интервалами 5–25 с на протяжении ~50 минут), `PATCH /llm-knowledge/{uuid}/files`
   и `DELETE /activities/mass-delete` всё это время отвечали 423 «Коллекция заблокирована до окончания
   обработки контекста». Повторная загрузка **другого** (ранее не встречавшегося) содержимого
   (`soups.pdf`, `soups.txt`, `pea_soup.md` — в трёх последующих прогонах) каждый раз обрабатывалась
   штатно за 15–40 с. Похоже на то, что фоновая задача экстракции текста не диспетчеризуется повторно
   для уже известного (по хэшу) файла, если он прежде был привязан к другому (в т.ч. уже удалённому)
   знанию — присвоенный статус из прошлой обработки не копируется в новую связку знание-файл.
   **Не починено (не входит в объём разведки), требует внимания разработки.**

2. **Незакрытый артефакт разведки**: активити `Автотест_AIChatRecon_1791400464` (id **7460**,
   `--env develop`) не удалена — попадает под дефект №1. Удаление пытались многократно в течение
   ~50 минут (включая попытки снять блокировку через выключение переключателя и экспорт истории,
   которые сами по себе не заблокированы 423, но не разблокируют `mass-delete`). Активити содержит
   один файл (`soups.docx`) с вечным статусом `pending`, переключатель выключен (`is_enabled: false`
   установлен в ходе разведки), реальных слушателей не назначено. **Требует ручного вмешательства
   (БД/очередь) для удаления — автотестовыми средствами не вышло.**

3. Подтверждён (не новый) факт из плана: расхождение D2 — у скан-pdf (`empty_context`) общая подпись
   «Не удалось обработать часть файлов.» без упоминания «текст не найден» — именно так и выглядит
   `activity-details-ai-chat-status_error` в разведке.

### Примечание к шагу 23/31 (путь «поток»)

Назначение в поток (`created_program` → `created_stream` → `created_module` →
`tincan_ep.assign_to_module`) у существующих тестов (`tests/ui/courses/tincan/stream/test_user_tincan_flow.py`)
уже имеет документированный `xfail`: карточка программы показывает вкладки «Расписание»/«Курсы и тесты»
неактивными, пока не развёрнута строка модуля — курс внутри модуля недостижим текущим page-объектом.
Поскольку кнопка чата рендерится тем же компонентом плеера независимо от способа назначения (поток или
индивидуальное обучение — подтверждено структурой `aside.player-chat` в коде фронта, который не завязан
на источник назначения), для `ai_chat`-тестов целесообразно использовать **индивидуальное обучение**
как основной путь (как и было сделано в этой разведке) и не наследовать дефект навигации потока;
отдельный тест на поток для `ai_chat` добавлять не планируется, пока дефект навигации не исправлен.
