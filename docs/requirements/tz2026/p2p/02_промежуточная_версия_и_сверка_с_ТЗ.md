ВАЖНО: промежуточная версия

В карточке ПЗ:

1. Название, описание, обложка, файл задания.
2. Режим проверки: обычная проверка / взаимопроверка.
3. Конструктор оценивания.
   1. В ТЗ это описано как возможность создать индивидуальную шкалу для каждого ПЗ типа «взаимопроверка»: неограниченное количество блоков вопросов, критериев оценки и разные типы вопросов — десятибалльная шкала, одиночный/множественный выбор и ввод слова.
4. Блоки вопросов и критерии оценки.
   1. «После проведения процедуры оценки, все значения в рамках одной практической работы одного слушателя должны агрегироваться и слушатель должен получать одну итоговую оценку его работы (общая оценка, а также значения по всем критериям).»
5. Типы вопросов: шкала, одиночный/множественный выбор, ввод текста.

В потоке:

1. Кому доступна проверка: слушателям потока, внешним проверяющим по ссылке, назначенным проверяющим/преподавателям.
2. Лимит количества проверок.
3. Сроки открытия и закрытия проверки.
4. Распределение работ между проверяющими

Кратко: что нужно сделать
Нужно реализовать функциональность peer-to-peer / взаимопроверки практических заданий.
Функциональность не реализуется как новый тип практического задания.
Используется существующий тип активности «Практическое задание».
В базовой карточке ПЗ добавляется только параметр, который разрешает использовать это ПЗ для взаимопроверки.
Например:
«Доступно для взаимопроверки»
Все остальные настройки взаимопроверки выполняются уже при назначении ПЗ в конкретный поток/модуль.
Функциональность должна включать
1. Параметр в карточке практического задания
В существующую карточку активности «Практическое задание» нужно добавить параметр:
«Доступно для взаимопроверки»
Этот параметр определяет, можно ли использовать данное ПЗ в сценариях peer-to-peer проверки.
В самой карточке ПЗ остаются текущие поля:

* изображение на обложку;
* название в админке;
* название на внешке;
* продолжительность;
* категория;
* описание;
* основной документ;
* дополнительные документы;
* преподаватели;
* проверяющие;
* система оценивания;
* сертификат.

Подробные правила взаимопроверки в карточке ПЗ не настраиваются.

2. Настройка взаимопроверки на стороне потока/модуля
Все детальные настройки взаимопроверки выполняются на уровне конкретного назначения ПЗ в поток/модуль.
Это нужно для того, чтобы одно и то же ПЗ можно было использовать по-разному в разных потоках.
Например:

* в одном потоке ПЗ проверяет преподаватель;
* во втором потоке то же ПЗ используется для взаимопроверки слушателями;
* в третьем потоке к проверке добавляются внешние проверяющие по ссылке.

То есть базовая активность остаётся общей, а сценарий проверки определяется в конкретном потоке.

3. Включение взаимопроверки в потоке
При добавлении ПЗ в поток/модуль администратор должен иметь возможность включить режим:
«Взаимопроверка»
Этот режим доступен только для тех ПЗ, у которых в базовой карточке включён параметр:
«Доступно для взаимопроверки»
Если параметр в базовом ПЗ не включён, то в потоке такое ПЗ нельзя настроить как взаимопроверку.
4. Ограничение для групповых ПЗ
Групповые практические задания не должны проверяться через взаимопроверку.
Для групповых ПЗ режим peer-to-peer должен быть недоступен.
В интерфейсе это может отображаться как ограничение:
«Взаимопроверка недоступна для групповых практических заданий»
Таким образом:

* индивидуальные ПЗ могут участвовать во взаимопроверке;
* групповые ПЗ не участвуют во взаимопроверке;
* групповые ПЗ проверяются по стандартному сценарию.


5. Выбор участников проверки в потоке
В настройках ПЗ внутри потока/модуля администратор задаёт, кто может проверять работы.
Доступные варианты:

* слушатели этого же потока;
* назначенные проверяющие;
* преподаватели;
* внешние пользователи по индивидуальной ссылке.

Настройка выполняется не в базовой карточке ПЗ, а именно в конкретном потоке.

6. Настройка количества проверок
4.2.2.2.1.1.Для слушателей потока и неавторизованных пользователей по умолчанию должна быть возможность проверки практического задания неограниченное количество раз, но должна быть возможность указания определенного количества проверок (N проверок для слушателей и N проверок для неавторизованных пользователей, либо N проверок всего).
В настройках взаимопроверки на уровне потока администратор задаёт количество проверок.
Например:

* сколько проверок нужно на одну работу;
* сколько работ должен проверить один слушатель;
* сколько внешних проверок допускается;
* нужна ли обязательная проверка преподавателем;
* когда работа считается полностью проверенной.


7. Механизм оценивания
похоже на тест как в аос
Для проверки используется механизм оценивания, близкий к тесту/форме.
Проверяющий открывает работу и заполняет форму оценки.
Форма может включать:

* критерии;
* шкалы;
* варианты ответа;
* текстовые комментарии;
* итоговый комментарий.

Настройка критериев выполняется в рамках задания/назначения в потоке, чтобы оценивание соответствовало конкретному сценарию обучения.

8. Процесс сдачи работы слушателем
Слушатель проходит обычное практическое задание:

* открывает ПЗ;
* изучает описание и документы;
* выполняет работу;
* отправляет ответ.

После отправки работа попадает в проверку.
Если для этого ПЗ в потоке включена взаимопроверка, работа становится доступна другим проверяющим согласно настройкам потока.

9. Процесс проверки работы
Проверяющий получает доступ к работе и оценивает её по заданным критериям.
Проверяющим может быть:

* другой слушатель потока;
* преподаватель;
* назначенный проверяющий;
* внешний пользователь по ссылке.

Слушатель не должен проверять собственную работу.

10. Агрегация результатов
После завершения нужного количества проверок система формирует итоговый результат по работе.
Итоговый результат должен включать:
4.2.2.4.После проведения процедуры оценки, все значения в рамках одной практической работы одного слушателя должны агрегироваться и слушатель должен получать одну итоговую оценку его работы (общая оценка, а также значения по всем критериям).
4.2.3.2.После завершения проверки практического задания, у слушателя должна быть возможность просмотра итоговой оценки за работу, а также общие оценки по критериям.

* итоговую оценку;
* оценки по критериям;
* комментарии проверяющих, если они предусмотрены;
* статус проверки.

Если предусмотрено подтверждение преподавателем, итоговая оценка сначала попадает на верификацию.
11. Просмотр результата слушателем
После завершения проверки слушатель должен видеть результат по своей работе.
В результате отображается:

* статус проверки;
* итоговая оценка;
* оценки по критериям;
* комментарии, если они разрешены к показу.

12. Уведомления
Система должна уведомлять участников процесса.
Слушателя, который сдал работу:

* что работа отправлена;
* что работа находится на проверке;
* что проверка завершена.

Слушателя, который проверяет:

* что ему доступна работа для проверки;
* что проверку нужно выполнить.

Преподавателя или администратора:

* что проверки проведены;
* что результат готов;
* что требуется верификация, если она включена.


13. Отчёты и статистика
В админке должны отображаться данные по взаимопроверке.
Минимально:

* список сданных работ;
* статус каждой работы;
* количество выполненных проверок;
* кто проверял;
* итоговая оценка;
* оценки по критериям;
* требуется ли подтверждение преподавателя.

Также должна фиксироваться активность проверяющих:

* сколько работ проверил пользователь;
* какие проверки завершены;
* какие проверки просрочены;
* какие проверки учтены в результате.


14. Сертификаты за проверку
Если в потоке включена выдача сертификатов за участие в проверке, система должна учитывать выполненные проверки.
Сертификат выдаётся пользователю за факт участия в проверке по правилам, заданным в потоке.
Например:

* проверил нужное количество работ;
* заполнил обязательные критерии;
* проверка была принята системой;
* проверка не была отменена преподавателем.


Путь пользователя: администратор

1. Администратор заходит в админку.
2. Открывает базу активностей.
3. Создаёт или редактирует существующее практическое задание.
4. Заполняет стандартные поля ПЗ:
   * обложка;
   * название в админке;
   * название на внешке;
   * продолжительность;
   * категория;
   * описание;
   * основной документ;
   * дополнительные документы;
   * преподаватели;
   * проверяющие;
   * система оценивания.
5. Включает параметр «Доступно для взаимопроверки».
6. Сохраняет ПЗ.
7. Переходит в настройки потока/модуля.
8. Назначает это ПЗ в поток/модуль.
9. В настройках назначения включает режим «Взаимопроверка».
10. Настраивает, кто может проверять:

* слушатели потока;
* преподаватели;
* назначенные проверяющие;
* внешние пользователи по ссылке.

11. Настраивает количество проверок:

* сколько проверок требуется на одну работу;
* сколько работ должен проверить один слушатель;
* нужны ли внешние проверки;
* нужна ли проверка преподавателем.

12. Настраивает форму оценивания:

* критерии;
* шкалы;
* вопросы;
* комментарии;
* обязательные поля.

13. Настраивает правила показа результата слушателю.
14. При необходимости включает сертификаты за участие в проверке.
15. Публикует ПЗ в потоке.
16. Отслеживает сдачу работ.
17. Отслеживает ход проверок.
18. Просматривает итоговые оценки.
19. При необходимости подтверждает результаты.
20. Смотрит отчёты и статистику по взаимопроверке.


Путь пользователя: слушатель, который сдаёт работу

1. Слушатель заходит в личный кабинет.
2. Видит назначенное практическое задание.
3. Открывает задание.
4. Изучает описание, документы и требования.
5. Выполняет работу.
6. Загружает ответ или вводит его в интерфейсе.
7. Отправляет работу.
8. Система фиксирует сдачу.
9. Если в потоке включена взаимопроверка, работа попадает в очередь проверки.
10. Слушатель видит статус работы:

* «Работа отправлена»;
* «Ожидает проверки»;
* «Проверяется»;
* «Проверка завершена»;
* «Ожидает подтверждения преподавателя».

11. После завершения проверки слушатель открывает результат.
12. Видит итоговую оценку, оценки по критериям и комментарии, если они доступны.


Путь пользователя: слушатель, который проверяет работу

1. Слушатель заходит в личный кабинет.
2. Видит уведомление или блок «Доступны работы для проверки».
3. Открывает список работ, которые ему доступны.
4. Система не показывает ему его собственную работу.
5. Слушатель выбирает работу для проверки.
6. Изучает ответ другого слушателя.
7. Открывает форму оценивания.
8. Заполняет критерии:
   * ставит баллы;
   * выбирает варианты;
   * пишет комментарии;
   * заполняет обязательные поля.
9. Отправляет проверку.
10. Система фиксирует результат проверки.
11. Если по работе достигнуто нужное количество проверок, работа больше не выдаётся другим проверяющим.
12. Проверка учитывается в статистике активности пользователя.
13. Если включены сертификаты, выполненная проверка учитывается для получения сертификата.


Путь пользователя: внешний проверяющий по ссылке

1. Внешний пользователь получает индивидуальную ссылку на проверку работы.
2. Переходит по ссылке.
3. Авторизация по логину и паролю не требуется.
4. Система открывает только ту работу, которая привязана к ссылке.
5. Внешний проверяющий изучает работу.
6. Заполняет форму оценки по критериям.
7. Отправляет результат.
8. Система сохраняет оценку.
9. Оценка учитывается в итоговом результате работы.
10. После отправки проверки ссылка больше не позволяет повторно отправить оценку, если это не разрешено настройками потока.

Нюансы, которые нужно зафиксировать

1. Новый тип ПЗ не создаётся
Используется существующий тип активности «Практическое задание».
2. В карточке ПЗ добавляется только параметр
В базовой карточке ПЗ добавляется признак «Доступно для взаимопроверки».
3. Все подробные настройки — на стороне потока/модуля
Участники проверки, лимиты, критерии, ссылки, уведомления и сертификаты настраиваются при назначении ПЗ в поток/модуль.
4. Групповые ПЗ не участвуют во взаимопроверке
Для групповых практических заданий режим peer-to-peer недоступен.
5. Слушатель не может проверять свою работу
Система должна исключать собственную работу из списка доступных для проверки.
6. Оценивание работает через форму/механизм теста
Проверяющий заполняет критерии оценки как форму.
7. Результат формируется после нужного количества проверок
Итоговая оценка появляется после выполнения правил проверки, заданных в потоке.
8. Преподаватель может подтверждать результат
Если в потоке включена верификация, итоговая оценка должна быть подтверждена преподавателем.
9. Сертификат выдаётся за участие в проверке
Сертификат связан не с фактом сдачи ПЗ, а с выполнением проверок.
10. Отчётность нужна по работам и проверяющим
Администратор должен видеть, кто сдал работу, кто проверил, сколько проверок выполнено и какой итоговый результат сформирован.

количество проверок одной работы внешними пользователями;
общее количество проверок одной работы.


5. «Нужна ли обязательная проверка преподавателем»
В ТЗ сказано, что преподаватели могут проверять, и каждый указанный преподаватель должен иметь возможность проверить ПЗ один раз . Но обязательная проверка преподавателем не прописана.
В смете есть формулировка, что преподавателю нужно сообщить, что проверки проведены и нужно верифицировать оценки . Но механика обязательности не раскрыта.
Лучше заменить на:
уведомление преподавателя о проведённых проверках и необходимости верификации оценок.
И убрать:
нужна ли обязательная проверка преподавателем;
если предусмотрено подтверждение преподавателем;
итоговая оценка сначала попадает на верификацию;
при необходимости подтверждает результаты.
Или оставить только как «требует уточнения».


6. «Работа больше не выдаётся другим проверяющим»
В ТЗ это есть частично: если количество проверок ограничено, при достижении лимита возможность проверки должна закрываться . Формулировка нормальная, но лучше привязать к лимиту:
Если по работе достигнут установленный лимит проверок, возможность дальнейшей проверки закрывается.


7. «Комментарии проверяющих»
В ТЗ прямо указаны типы вопросов: десятибалльная шкала, ОиМ, МиМ и ввод слова . Комментарии как отдельная сущность не указаны, но «ввод слова» можно трактовать как текстовый ввод.
Лучше писать осторожно:
текстовый ответ / ввод слова.
А не:
комментарии проверяющих, итоговый комментарий.


8. «Статусы: Работа отправлена / Ожидает проверки / Проверяется / Ожидает подтверждения преподавателя»
В ТЗ таких статусов нет. Это нормальная детализация UX, но не требование из ТЗ.
Лучше убрать конкретные названия статусов или написать:
Система отображает пользователю текущий статус работы и проверки.


9. «Слушатель не может проверять собственную работу»
В ТЗ это прямо не написано. Но из логики взаимопроверки «у остальных слушателей потока должна быть возможность оценить эту работу» следует, что проверяют именно другие слушатели .
Можно оставить, но как вывод из требования:
Система не должна выдавать слушателю его собственную работу на проверку, так как в ТЗ указана проверка работы остальными слушателями потока.


10. «Проверка была принята системой / не была отменена преподавателем»
Этого нет ни в ТЗ, ни в смете. В смете есть выдача сертификатов за проведённую оценку, генератор, поиск по сертифицированным и отправка сертификатов . Условий «принята системой» или «не отменена преподавателем» нет.
Лучше заменить на:
сертификат выдаётся за проведённую оценку по правилам, которые необходимо уточнить в ДТТ.


11. «Просроченные проверки»
В ТЗ и смете нет сроков проверки и просрочек. Лучше убрать.


12. «Настройка правил показа результата слушателю»
В ТЗ есть только то, что после завершения проверки слушатель должен иметь возможность просмотра итоговой оценки и общих оценок по критериям . Настроек показа нет.
Лучше заменить на:
после завершения проверки слушателю отображаются итоговая оценка и оценки по критериям.


Что точно есть в ТЗ/смете и можно оставлять
Оставляем без сомнений:

1. Проверка работ слушателями потока, неавторизованными пользователями и преподавателями .
2. Выбор, кому доступна оценка: слушателям потока, неавторизованным по ссылке, проверяющим .
3. Ограничение: только преподавателей выбрать нельзя, обязательно должны быть слушатели или неавторизованные пользователи .
4. Настройка количества проверок: неограниченно по умолчанию или N проверок .
5. Уникальная ссылка для внешней проверки каждого ответа .
6. Каждый указанный преподаватель может проверить ПЗ один раз .
7. Шкала оценивания с блоками вопросов, критериями и типами вопросов .
8. Сертификаты за проверку ПЗ .
9. Агрегация оценок в одну итоговую оценку и оценки по критериям .
10. Просмотр слушателем итоговой оценки и оценок по критериям .
11. Уведомления, статистика вклада, отчёты по оценкам и сертификаты — из сметы .

Итог
В текущем тексте нужно пометить как изменение/уточнение, а не как исходное ТЗ:

* не создавать новый тип ПЗ;
* сделать только параметр в карточке ПЗ;
* все настройки вынести на уровень потока/модуля;
* запретить групповые ПЗ.

А лучше убрать или смягчить:

* обязательную проверку преподавателем;
* подтверждение результата преподавателем;
* «работа принята системой / отменена преподавателем»;
* просроченные проверки;
* конкретные статусы;
* отдельные комментарии, если они не описаны как текстовый ввод;
* «сколько работ должен проверить один слушатель» в жёсткой форме.
