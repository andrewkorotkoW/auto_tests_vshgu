Практическое задание: режим взаимопроверки peer-to-peer
Выделение в документе: зелёным — изменено/уточнено по итогам встречи с заказчиком; жёлтым — вопрос, который требует подтверждения заказчика.
1. Общая логика
Дорабатывается существующая активность «Практическое задание» (ПЗ). Взаимопроверка peer-to-peer реализуется как отдельная настройка существующего ПЗ, без создания отдельного бизнес-типа активности.
Краткое ТЗ, п. 1.1.1.1 — Создание возможности интеграции в образовательный процесс заданий с взаимопроверкой в одном потоке.
Критерии взаимопроверки относятся к самому ПЗ и переиспользуются при назначении этого ПЗ в потоки. Параметры конкретного запуска, состав участников и распределение работ задаются на уровне потока.

Краткое ТЗ, п. 1.1.2.4 — Функциональность, обеспечивающая достижение каждой бизнес-потребности, должна являться отдельной настройкой для активити типа «Практическое задание».
Вопрос к заказчику: Нужно ли иметь в карточке ПЗ отдельное верхнеуровневое разрешение внешней проверки, либо внешние проверяющие всегда добавляются только в настройках конкретного потока? На встрече место этой настройки окончательно не зафиксировано.
3. Роли и доступные интерфейсы
Краткое ТЗ, п. 1.1.2.1 — Должна быть реализована возможность проверки «Практических заданий» слушателями потока и сторонними пользователями.
Краткое ТЗ, п. 1.1.4.1 — Слушателям должен быть предоставлен доступ в имеющийся интерфейс проверки практических заданий. Примечание: на текущий момент доступ предоставлен Администраторам, Администраторам организации, Поддержке, Менеджерам, Преподавателям.
3.1. Проверяющий и преподаватель
В контексте ПЗ необходимо разделять назначение пользователя на конкретное задание и его системную роль.
• Проверяющий — пользователь, назначенный на конкретное ПЗ. Он получает доступ к работам этого ПЗ, проверяет ответы, может вернуть работу на доработку, выставить и изменить итоговый результат.
• Преподаватель — системная роль, предоставляющая доступ к интерфейсу проверки практических заданий.
• При назначении пользователя проверяющим на ПЗ система автоматически должна назначить ему роль «Преподаватель», если этой роли у него ещё нет.
• Наличие роли «Преподаватель» само по себе не является назначением на конкретное ПЗ: перечень доступных для проверки работ определяется назначениями пользователя как проверяющего.
• В рамках непосредственной проверки ПЗ функциональные возможности совпадают: «проверяющий» определяет связь пользователя с конкретным ПЗ, а «преподаватель» — системные права доступа к интерфейсу проверки.

Пользователь
Что видит и делает
Администратор / администратор организации / поддержка / менеджер
Видит все работы потока, назначения, внешние ссылки, статусы, результаты по критериям, статистику и отчёты. Сам по себе не получает право выставлять итоговый результат: для этого должен быть назначен проверяющим ПЗ.
Проверяющий ПЗ
Видит список работ по назначенному ПЗ, открывает работу и файлы, видит результаты всех peer-проверок, агрегированные значения и комментарии. Может вернуть работу на доработку, выставить и изменить итоговый результат.
Преподаватель
Системная роль, предоставляющая доступ к интерфейсу проверки ПЗ. При назначении пользователя проверяющим роль «Преподаватель» назначается автоматически, если её ещё нет. Сама по себе роль не назначает пользователя проверяющим конкретного ПЗ.
Слушатель-проверяющий
Видит только назначенные ему чужие работы. Открывает работу и заполняет форму критериев. Собственную работу не получает. Итоговый результат по ПЗ не выставляет.
Внешний неавторизованный проверяющий
По своей персональной ссылке видит список всех сданных работ по назначенному ему ПЗ в конкретном потоке и может последовательно их проверять. Полноценного личного кабинета не получает.
Автор работы
Видит статус своей работы, одну итоговую оценку и значения по всем критериям. Способ отображения отдельных peer-проверок, текстовых комментариев и данных проверяющих требует подтверждения.


В соответствии с кратким ТЗ автор работы после проведения процедуры проверки должен получать одну итоговую оценку и значения по всем критериям.

Вопрос к заказчику: Что после отправки своей проверки должен видеть слушатель-проверяющий: только собственные ответы по критериям или также агрегированную статистику и итоговый результат по чужой работе?
4. Настройки в карточке ПЗ
4.1. Включение взаимопроверки
В карточке ПЗ добавляется настройка «Включить взаимопроверку». Если она выключена, ПЗ работает по текущей стандартной логике.
Отключение взаимопроверки после запуска переключатель блокируется с момента появления первой сданной работы по ПЗ в потоке, участвующей во взаимопроверке? 
4.2. Штатные проверяющие
Используется текущий механизм назначения проверяющих ПЗ. Для выбора доступны те пользователи, которых система уже позволяет назначать проверяющими в существующем ПЗ.
Слушатели-проверяющие, распределённые внутри потока, не добавляются в базовый список проверяющих карточки ПЗ: их назначения относятся только к конкретному потоку и отображаются в его списке работ/назначений.
5. Критерии оценки
Для каждого ПЗ создаётся собственная форма критериев. Заказчику не принципиально, будет ли технически использован существующий опрос/тест или отдельный конструктор; это решение переносится на техническое проектирование.
Краткое ТЗ, п. 1.1.1.2 — Создание возможности создания в системе индивидуальных критериев (как качественных, так и количественных) проверки практических заданий.
Краткое ТЗ, п. 1.1.3.2 — Должен быть реализован конструктор формирования перечня критериев, по достижению которых будет оцениваться практическое задание.
5.1. Количественные и качественные критерии
• Количественные критерии — критерии, результат которых представляется числовым значением, например оценкой по шкале. Система сохраняет значение каждого проверяющего; по нескольким проверкам рассчитывается среднее арифметическое.
• Качественные критерии — критерии, по которым проверяющий предоставляет текстовую оценку, комментарий или иную качественную обратную связь. Такие ответы сохраняются отдельно, численно не агрегируются и отображаются списком.
• При одновременном использовании количественных и качественных критериев в результатах должны быть доступны как агрегированные количественные значения, так и качественные ответы проверяющих.
• Дополнительно форма может поддерживать критерии с одиночным и множественным выбором. Такие варианты не относятся автоматически к количественным или качественным; способ их агрегирования и представления в отчёте определяется отдельно.
5.2. Структура и изменение формы критериев
• Отдельная бизнес-механика весов критериев/вариантов ответа в текущий объём не закладывается.
• После начала получения peer-проверок нельзя добавлять или удалять критерии. Допускается исправление текста существующего критерия без изменения его смысловой структуры.
Вопрос к заказчику: Какой стандартный набор критериев должен автоматически создаваться для нового P2P-ПЗ? Заказчик подтвердил, но нужен состав шаблона.
6. Распределение работ между слушателями
Для слушателей потока должны поддерживаться оба режима распределения — ручной и автоматический.
Краткое ТЗ, п. 1.1.3.1 — Должна быть возможность выбора для проверки слушателей с потока в ручном режиме и в автоматическом режиме.
6.1. Ручной режим
• Менеджер/администратор вручную назначает конкретному слушателю конкретные чужие работы.
• Собственная работа слушателю не назначается.
6.2. Автоматический режим
• Система автоматически распределяет чужие работы между слушателями потока.
• В настройках задаётся «Количество работ для проверки одним слушателем». Например, при значении 2 система назначает каждому слушателю до 2 чужих работ.
• Минимальное количество peer-проверок, которое должна получить одна работа, задаётся отдельно. Этот параметр относится к самой работе и применяется независимо от выбранного ручного или автоматического режима распределения.
Вопрос к заказчику: Какой точный алгоритм автоматического распределения использовать: случайный, с выравниванием нагрузки, по очереди или иной? На встрече обязательность автоматического режима подтверждена, но алгоритм не выбран.
Вопрос к заказчику: Можно ли запустить P2P в потоке так, чтобы ни один слушатель не проверял работы других слушателей, а проверка выполнялась только штатными или внешними проверяющими?
6.3. Ограничение для внешних проверяющих
Настройки ручного/автоматического распределения и «Количество работ для проверки одним слушателем» применяются только к авторизованным слушателям потока.
Для внешнего неавторизованного проверяющего эти ограничения не применяются: по его персональной ссылке ему выводится весь список сданных работ выбранного ПЗ в данном потоке.
7. Внешняя проверка без авторизации
Внешний проверяющий создаётся на уровне конкретного потока для выбранного ПЗ.
Краткое ТЗ, п. 1.1.1.3 — Создание возможности проверки практических заданий лицами, не имеющими учётной записи в Системе.
Краткое ТЗ, п. 1.1.3.3 — Должна быть реализована возможность формирования ссылок для проверки практических заданий сторонними пользователями.
1. Менеджер выбирает ПЗ и добавляет внешнего проверяющего.
2. Указывает ФИО. Email — опционально.
3. Система создаёт отдельную персональную ссылку для этого внешнего проверяющего.
4. По ссылке проверяющий видит список всех сданных работ по этому ПЗ в данном потоке.
5. Он открывает любую работу из списка, заполняет критерии, сохраняет проверку и может перейти к следующей работе.
6. На одно ПЗ можно добавить несколько внешних проверяющих; у каждого своя ссылка.
7. Полное совпадение ФИО допускается. Уникальность должна обеспечиваться внутренним идентификатором/ссылкой, а не ФИО.
8. Ссылка используется повторно: внешний проверяющий может снова перейти по ней и вернуться к своему списку работ.
Если указан email, система может отправить на него уведомление о доступе к проверке. Если email отсутствует, менеджер копирует ссылку и передаёт её самостоятельно по внешнему каналу.
Вопрос к заказчику: Нужно ли ограничивать срок действия внешней ссылки и нужна ли менеджеру возможность вручную отозвать/деактивировать её?
Вопрос к заказчику: Нужно ли внешнему проверяющему разрешать возвращать работу на доработку? Если да, должен ли он после повторной сдачи видеть и переоценивать новую версию по той же ссылке?
Вопрос к заказчику: Какие события должны инициировать email-уведомление внешнему проверяющему: только создание доступа, появление новых работ, повторная сдача после доработки и/или напоминания?
8. Редактирование peer-проверки и возврат работы на доработку
8.1. Редактирование своей peer-проверки
• До финального подтверждения слушатель-проверяющий должен иметь возможность вернуться к своей проверке и изменить выставленные значения.
• В интерфейсе требуется отдельное действие финального подтверждения/сохранения проверки, после которого обычное редактирование блокируется.
8.2. Возврат на доработку
• Сохраняется существующая возможность ПЗ вернуть работу на доработку.
• Возврат выполняет штатный проверяющий ПЗ. Слушатель-проверяющий сам не является штатным проверяющим и итоговый статус работы не меняет.
• После возврата автор дорабатывает работу и отправляет новую версию.
• После повторной сдачи запускается повторный цикл проверки этой работы. Пользователи, которые уже проверяли предыдущую версию, должны снова получить возможность открыть работу и скорректировать свои оценки с учётом новой версии.
• В интерфейсе должно быть видно, что работа была доработана и доступна повторная оценка.
Вопрос к заказчику: Что происходит с результатами предыдущего цикла после повторной сдачи: (1) старые оценки сохраняются отдельной версией только в истории, а новая оценка создаётся заново; (2) старые значения остаются текущими и проверяющий редактирует их; (3) старые результаты сбрасываются полностью? На встрече подтвердили возможность переоценки после доработки, но способ хранения предыдущих результатов не определили.
Вопрос к заказчику: Что происходит с незавершёнными peer-проверками в момент возврата на доработку: они приостанавливаются и затем возобновляются, отменяются и назначаются заново или остаются без изменений?
Вопрос к заказчику: После повторной сдачи сохраняются прежние назначения слушателей-проверяющих или система выполняет новое распределение по правилам текущего режима?
9. Итоговый результат
Краткое ТЗ, п. 1.1.2.2 — После проведения процедуры проверки все оценки в рамках одной практической работы одного слушателя должны агрегироваться, и слушатель должен получать одну итоговую оценку его работы (общая оценка, а также значения по всем критериям).
Если в ПЗ назначен хотя бы один штатный проверяющий, система сама итоговый результат по peer-оценкам не выставляет.
• Любой пользователь, назначенный проверяющим данного ПЗ, может выставить итоговый результат.
• Проверяющий может изменить уже выставленный итоговый результат в рамках текущей логики ПЗ.
• Агрегированные peer-оценки и комментарии используются как информация для принятия решения и не подменяют итоговую оценку проверяющего.
ПЗ может быть создано без назначенных штатных проверяющих. Для такого сценария на встрече обсуждалось автоматическое формирование результата, но решение не подтверждено.
Вопрос к заказчику: Если у ПЗ нет ни одного штатного проверяющего, должна ли система автоматически выставлять итоговый результат? Предложенный вариант: в форме есть обязательный системный критерий «Общая оценка за ПЗ», каждый peer-проверяющий выставляет общую оценку, система считает среднее арифметическое этих общих оценок и использует его как итоговый результат.
Вопрос к заказчику: Если автоматический итог используется, когда он фиксируется: после минимального количества проверок, после окончания срока P2P или по отдельному действию менеджера?
Вопрос к заказчику: Может ли штатный проверяющий выставить итоговый результат в любой момент после сдачи работы, независимо от количества полученных peer-проверок, или для выставления результата должно быть выполнено отдельное условие?
10. Завершение взаимопроверки и статусы
При реализации максимально переиспользуются существующие статусы ПЗ. Новые статусы вводятся только если текущих состояний недостаточно.
• Не сдано / работа не отправлена.
• Сдано / доступно для проверки.
• На взаимопроверке.
• Возвращено на доработку.
• Итоговый результат выставлен.
10.1. Критерий завершения взаимопроверки
Для каждой сданной работы задаётся минимальное количество peer-проверок, которое необходимо получить. При этом само достижение этого количества не должно трактоваться системой однозначно до подтверждения бизнес-правила завершения.
Вопрос к заказчику: Что именно считается завершением взаимопроверки по работе: получение минимально необходимого количества peer-проверок, наступление установленного срока, ручное завершение менеджером или комбинация этих условий?
Вопрос к заказчику: После получения минимально необходимого количества peer-проверок нужно автоматически закрыть возможность дальнейшей проверки этой работы или только считать минимальное количество выполненным, продолжая принимать дополнительные проверки?
Вопрос к заказчику: Что должна делать система, если к установленному сроку работа не набрала минимально необходимое количество peer-проверок?

11. Отчёт и отображение результатов

По результатам P2P должна быть реализована выгрузка отчёта. На встрече заказчик не подтвердил окончательный состав, формат и место скачивания отчёта.
Вопрос к заказчику: Какие данные должны входить в отчёт: автор работы, статус, количество назначенных/выполненных проверок, список проверяющих, значения по критериям, средние значения, текстовые комментарии, итоговый результат, история доработок и переоценок?

Вопрос к заказчику: В каких форматах требуется отчёт: PDF, Word и/или другой формат?
Вопрос к заказчику: Где должна находиться выгрузка: в админке потока, в интерфейсе штатного проверяющего, на внешке у автора работы или в нескольких местах?

12. Уведомления авторизованных слушателей
Краткое ТЗ, п. 1.1.3.5 — Должна быть реализована возможность уведомлять:
• через пользовательский интерфейс — слушателей потока о практических заданиях, доступных к проверке;
• по иным каналам связи — сторонних пользователей.
Авторизованные слушатели потока должны получать через пользовательский интерфейс уведомления о работах, назначенных им для peer-проверки.
Вопрос к заказчику: Нужно ли уведомлять слушателя повторно, если проверенная им работа была возвращена на доработку и после повторной сдачи снова доступна для переоценки?
13. Сертификаты
Краткое ТЗ, п. 1.1.1.4 — Создание возможности выдачи подтверждающего документа за проверку практического задания.
Краткое ТЗ, п. 1.1.2.3 — Должна быть реализована возможность выдачи сертификатов за проведенную оценку практических заданий.
Сертификат в рамках P2P выдаётся за выполнение проверок. Точная механика на встрече не была согласована и должна быть подтверждена заказчиком.
Вопрос к заказчику: За что именно выдаётся сертификат: за выполнение всех назначенных проверок в рамках одного ПЗ, за достижение заданного количества проверок или по другому правилу?
Вопрос к заказчику: Где задаётся порог/условие выдачи и к чему привязывается шаблон сертификата: к карточке ПЗ, конкретному потоку или разделу сертификатов?

Вопрос к заказчику: Если пользователь участвует в нескольких ПЗ/потоках, прогресс считается отдельно по каждому ПЗ в каждом потоке или суммарно?
Вопрос к заказчику: Получают ли сертификат штатные проверяющие ПЗ или только слушатели-проверяющие?
Вопрос к заказчику: Нужен ли сертификат внешнему неавторизованному проверяющему? На встрече этот сценарий оставили на отдельную проработку из-за возможной технической сложности.

В текущей системе существует ограничение на повторное использование одного и того же ПЗ в нескольких потоках одной программы. На встрече заказчик не подтвердил ни сохранение, ни снятие этого ограничения.
Вопрос к заказчику: Оставляем текущее ограничение без изменений в рамках P2P или дорабатываем механику повторного назначения одного ПЗ?
15. Журналирование
Краткое ТЗ, п. 1.1.5.1 — Должен быть определен перечень действий, которые должны журналироваться.
Должны журналироваться действия, влияющие на ход и результат взаимопроверки. Минимальный перечень:
• включение/изменение настроек P2P;
• назначение штатных проверяющих;
• ручное и автоматическое распределение peer-проверок;
• добавление/отзыв внешнего проверяющего и ссылки;
• отправка и изменение peer-проверки;
• возврат на доработку и повторная сдача;
• выставление и изменение итогового результата;
• формирование отчёта;
• выдача сертификата.
Вопрос к заказчику: Нужно ли дополнить перечень обязательных журналируемых действий для критериев приёмки?
16. Что не фиксируем как обязательную бизнес-реализацию
• Отдельный новый тип активности «ПЗ с взаимопроверкой» — не требуется.
• Отдельный флаг «Может выставлять итоговый результат» у штатного проверяющего — не требуется: любой назначенный проверяющий может выставить результат.
• Отдельная бизнес-механика весов критериев/вариантов ответа — не требуется в текущем реализации.
• Конкретный технический способ реализации конструктора критериев — не фиксируется на бизнес-уровне.
• Отдельная вторая статусная модель для каждой назначенной peer-проверки не является обязательной, если сценарий покрывается существующими статусами ПЗ и локальными состояниями интерфейса.
• Сценарий «Индивидуальные ПЗ в режиме самопроверки» в текущую P2P-доработку не включается.
