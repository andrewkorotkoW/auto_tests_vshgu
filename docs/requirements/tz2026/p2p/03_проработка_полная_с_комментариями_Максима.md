1. Что делаем
Дорабатываем существующую активность «Практическое задание» для сценария взаимопроверки peer-to-peer.
Новый тип активности не создаётся. Взаимопроверка реализуется как дополнительный режим работы существующего ПЗ.
В карточке ПЗ добавляется настройка:
«Включить взаимопроверку»
При выключенной настройке ПЗ работает по текущей стандартной логике.
При включённой настройке ПЗ работает по сценарию взаимопроверки:

1. слушатель отправляет работу;
2. работа становится доступна назначенным проверяющим;
3. слушатели-проверяющие и/или проверяющие заполняют форму оценки по критериям;
4. система сохраняет результаты проверок по каждому критерию;
5. после достижения требуемого количества проверок взаимопроверка по работе считается завершённой;
6. работа переходит в состояние ожидания итогового результата;
7. проверяющий с правом итогового решения смотрит результаты проверок и выставляет итоговый результат;
8. слушатель, сдавший работу, видит итоговый результат по своей работе;
9. система формирует отчёт по результатам взаимопроверки;
10. за выполнение назначенного объёма проверок может быть выдан сертификат.

Важно: система не выставляет итоговый зачёт / незачёт автоматически. Итоговый результат всегда выставляет проверяющий, у которого включено право итогового решения.
Критерии оценки описываются отдельно в разделе «Критерии оценки».
Статусы ПЗ и процесса проверки описываются отдельно в разделе «Статусная модель».
2. Роли в процессе
В процессе взаимопроверки участвуют следующие роли.
2.1. Слушатель
Слушатель:

* сдаёт свою работу по ПЗ;
* может проверять работы других слушателей потока, если для ПЗ включена взаимопроверка;
* не должен получать на проверку собственную работу;
* видит доступные ему задания на проверку;
* заполняет форму критериев по назначенным ему работам;
* не выставляет официальный итоговый зачёт / незачёт по чужой работе;
* после выставления итогового результата видит результат по своей работе.

Слушатель-проверяющий оценивает чужую работу только через критерии: шкалы, варианты выбора, текстовые комментарии.
2.2. Проверяющие из настроек ПЗ
Проверяющие выбираются в карточке ПЗ.
Проверяющие из настроек ПЗ:

* участвуют в проверке работ;
* видят работы, отправленные слушателями;
* видят результаты проверок по критериям;
* видят отчёт и статистику по взаимопроверке;
* могут проверять работы;
* могут иметь право выставлять итоговый результат по работе.

Для проверяющего может быть включена дополнительная настройка:
«Может выставлять итоговый результат»
В интерфейсе это может быть реализовано как галочка, звёздочка или иной признак напротив проверяющего.
Если у ПЗ несколько проверяющих, один или несколько из них могут быть отмечены как проверяющие с правом итогового решения.
Итоговый результат по работе выставляет только проверяющий, у которого включено право итогового решения.
2.3. Преподаватель
Преподаватель в ПЗ используется в основном для отображения во внешнем интерфейсе.
Комментарий Максима:
В ПЗ препод же чисто для картинки на внешке. Главный по делам в ПЗ - проверяющий.
Фиксируем:

* преподаватель может отображаться во внешнем интерфейсе как связанное с ПЗ лицо;
* бизнес-логика проверки должна быть завязана на проверяющих из настроек ПЗ;
* право выставления итогового результата определяется не ролью «преподаватель», а настройкой конкретного проверяющего.

Вопрос:

* Подтверждаем ли, что преподаватель в рамках P2P не является отдельной управляющей ролью, а все действия выполняются через проверяющих из настроек ПЗ?

2.4. Администратор / менеджер
Администратор или менеджер:

* включает или выключает режим взаимопроверки;
* настраивает критерии оценки;
* выбирает проверяющих в карточке ПЗ;
* настраивает параметры взаимопроверки при назначении ПЗ в поток;
* может просматривать результаты и отчёты;
* может управлять уведомлениями, если такая настройка будет реализована.

Если администратор должен изменить или выставить итоговый результат, он должен быть добавлен в список проверяющих и иметь право выставления итогового результата.
2.5. Неавторизованный пользователь
Неавторизованный пользователь может участвовать в проверке только по индивидуальной ссылке.
Он:

* переходит по ссылке;
* видит только работу и форму критериев;
* заполняет форму проверки;
* не видит личный кабинет;
* не видит список работ;
* не видит статистику;
* не видит отчёт;
* не получает отдельную логику личного кабинета.

Важно отдельно проработать адаптивный интерфейс проверки по ссылке, особенно для планшетов.
3. Где настраивается взаимопроверка
Настройки взаимопроверки нужно разделить на два уровня:

1. настройки в карточке ПЗ в базе активностей;
2. настройки ПЗ при назначении в поток.

3.1. Что настраивается в карточке ПЗ в базе активностей
В карточке ПЗ настраиваются параметры, которые относятся к самой активности и не зависят от конкретного потока.
В карточке ПЗ настраиваются:

* включение режима взаимопроверки;
* список проверяющих;
* право проверяющего выставлять итоговый результат;
* форма критериев оценки;
* разрешён ли возврат работы на доработку;
* базовое разрешение внешней проверки по ссылке, если этот сценарий нужен.

3.2. Что настраивается при назначении ПЗ в поток
При назначении ПЗ в поток настраиваются параметры, которые зависят от конкретного потока и состава слушателей.
В настройках ПЗ внутри потока настраиваются:

* какие слушатели участвуют во взаимопроверке;
* сколько работ должен проверить каждый слушатель;
* способ распределения работ между слушателями;
* параметры конкретного запуска ПЗ в потоке;
* ссылки для внешних проверяющих, если внешняя проверка включена;
* просмотр результатов и отчёта по конкретному потоку.

Важно: результаты взаимопроверки относятся не к базовой карточке ПЗ, а к конкретному назначению ПЗ в поток.
4. Настройки в карточке ПЗ в базе активностей
В карточке ПЗ добавляется настройка:
«Включить взаимопроверку»
Если настройка выключена, ПЗ работает как обычное практическое задание.
Если настройка включена, в карточке ПЗ становятся доступны дополнительные настройки взаимопроверки.
4.1. Проверяющие
В карточке ПЗ настраивается список проверяющих.
Все пользователи, добавленные в этот список, участвуют в проверке работ по данному ПЗ и имеют доступ к результатам взаимопроверки.
Для проверяющего может быть дополнительно включено право:
«Может выставлять итоговый результат»
Итоговый результат по работе выставляет только проверяющий, у которого включено это право.
4.2. Критерии оценки
В карточке ПЗ настраивается форма критериев оценки.
Критерии оценки понимаются как конструктор тестов / форма оценки.
Каждый вопрос формы - это отдельный критерий оценки.
Подробно критерии описаны в разделе «Критерии оценки».
4.3. Возврат на доработку
В карточке ПЗ можно добавить настройку:
«Разрешить возврат работы на доработку при взаимопроверке»
Если настройка выключена:

* проверяющие не могут вернуть работу на доработку;
* работа проходит цикл проверки без возврата;
* после завершения взаимопроверки работа ожидает итогового результата;
* итоговый результат выставляет проверяющий с правом итогового решения.

Если настройка включена:

* проверяющий может вернуть работу на доработку;
* при возврате одним из проверяющих проверка этой работы приостанавливается у всех проверяющих;
* после повторной сдачи нужно определить, запускается ли новый цикл проверки.

Вопрос:

* После повторной сдачи работы должен запускаться новый цикл взаимопроверки?
* Предыдущие результаты проверок должны сохраняться или сбрасываться?

4.4. Внешняя проверка по ссылке
В карточке ПЗ может быть настройка, разрешающая проверку по ссылке для внешних пользователей.
Предлагаемая логика:

* базовое разрешение внешней проверки хранить в карточке ПЗ;
* конкретные ссылки формировать уже в контексте потока и конкретной работы.

Вопрос:

* Эта настройка должна находиться в карточке ПЗ или только в настройках ПЗ внутри потока?

5. Настройки ПЗ при назначении в поток
Часть настроек задаётся не в карточке ПЗ, а при назначении ПЗ в конкретный поток, потому что они зависят от состава слушателей и сценария прохождения.
5.1. Участники взаимопроверки
При назначении ПЗ в поток система понимает список слушателей, которые участвуют в этом потоке.
Для режима взаимопроверки слушатели потока могут быть участниками проверки работ друг друга.
Фиксируем логику:

* P2P работает только в рамках потока;
* участниками P2P являются обучающиеся этого потока;
* слушатель не должен проверять собственную работу.

5.2. Количество работ на проверку
При назначении ПЗ в поток нужно добавить настройку:
«Сколько работ должен проверить каждый слушатель»
Например:

* каждый слушатель должен проверить 1 работу;
* каждый слушатель должен проверить 2 работы;
* каждый слушатель должен проверить N работ.

Эта настройка должна находиться именно в настройках ПЗ внутри потока, потому что количество проверок зависит от конкретного потока и количества слушателей.
5.3. Распределение работ между слушателями
Нужно определить способ распределения работ на проверку.
Возможные варианты:

1. автоматическое распределение системой;
2. ручное назначение администратором / менеджером.

Предлагаемая логика для первого этапа:

* система автоматически распределяет работы между слушателями;
* своя работа не попадает слушателю на проверку;
* количество назначенных работ определяется настройкой «Сколько работ должен проверить каждый слушатель».

5.4. Завершение взаимопроверки по работе
Для каждой сданной работы нужно определить, сколько проверок необходимо получить.
После достижения требуемого количества проверок взаимопроверка по работе считается завершённой.
Важно: завершение взаимопроверки не означает автоматическое выставление итогового результата.
Предлагаемая логика:

1. система ждёт, пока работа получит нужное количество проверок;
2. слушатели-проверяющие заполняют критерии;
3. после достижения нужного количества проверок работа переходит в статус «Взаимопроверка завершена, ожидает итогового результата»;
4. проверяющий с правом итогового решения смотрит результаты проверок;
5. проверяющий выставляет итоговый результат;
6. работа переходит в статус «Итоговый результат выставлен».

6. Ограничение: одно ПЗ в программе / потоке
В текущей системе есть ограничение: одно и то же ПЗ нельзя добавить в программу или поток дважды.
Комментарий Максима:
Это ограничение не от нас.
Для текущего ТЗ фиксируем:

* ограничение существует;
* в рамках P2P его не меняем;
* одна активность ПЗ может быть назначена в рамках программы / потока только по текущим правилам системы.

Вопрос для уточнения:

* Точно ли оставляем механику «одно ПЗ только один раз в программе / потоке» без изменений для первого этапа?

7. Критерии оценки
Критерии оценки - это форма оценки, собранная по логике конструктора тестов.
Администратор / менеджер создаёт набор вопросов, по которым проверяющий оценивает работу.
Каждый вопрос формы является отдельным критерием.
Критерии оценки настраиваются в карточке ПЗ в базе активностей, в отдельном блоке настроек, доступном при включённой настройке «Включить взаимопроверку».
7.1. Что делают слушатели-проверяющие
Слушатели, которые участвуют во взаимопроверке, не выставляют официальный итоговый зачёт / незачёт.
Они только:

* открывают назначенную им чужую работу;
* заполняют форму критериев;
* ставят оценки по шкалам, если такой критерий есть;
* выбирают варианты ответов, если такие критерии есть;
* оставляют текстовый комментарий, если такой критерий есть.

Слушатель-проверяющий даёт оценку по критериям, но не принимает финальное решение по ПЗ.
7.2. Итоговый результат
Итоговый результат - это отдельное действие.
Итоговым результатом может быть:

* зачёт / незачёт;
* итоговая оценка;
* итоговый балл;
* другой финальный результат, используемый в текущей логике ПЗ.

Итоговый результат всегда выставляет проверяющий с правом итогового решения.
Система не выставляет итоговый результат автоматически.
Результаты по критериям используются для:

* просмотра проверок;
* отчёта;
* статистики;
* помощи проверяющему при принятии итогового решения.

7.3. Использование конструктора тестов
Критерии оценки можно реализовывать на базе логики конструктора тестов / формы.
Вопрос для проработки:

* Можно ли использовать существующую механику опроса как основу для критериев?
* Но в тесте есть функционал весов?
* Если используется механика теста, какие лишние настройки нужно скрыть или отключить для сценария проверки ПЗ?

7.4. Типы критериев
Нужно поддержать следующие типы критериев:

1. Шкала - проверяющий выбирает значение по настраиваемой шкале.
2. Одиночный выбор - проверяющий выбирает один вариант ответа. В отчёте по такому критерию отображается гистограмма распределения ответов.
3. Множественный выбор - проверяющий может выбрать несколько вариантов ответа. В отчёте по такому критерию отображается гистограмма распределения ответов.
4. Текстовое поле - проверяющий оставляет текстовый комментарий. Текстовые ответы выводятся в отчёте списком.

Гистограмма для одиночного и множественного выбора - новое требование, ранее не описанное в исходном ТЗ. Гистограмма отображается в PDF/Word-отчёте и показывает, сколько проверяющих выбрали каждый вариант ответа.
7.5. Шкала
Шкала - это числовой или условно числовой критерий.
Примеры:

* от 1 до 5;
* от 1 до 10;
* своя настраиваемая шкала.

Комментарий Максима:
Может сделаем шкалу настраиваемой? Чтобы было неограниченное количество вариантов оценки в рамках шкалы. Но у каждого варианта должен быть «вес».
Фиксируем как новое требование:

* шкала должна быть настраиваемой;
* количество вариантов шкалы не должно быть жёстко ограничено только диапазоном 1–10;
* у каждого варианта шкалы может быть вес.

Важно: вес варианта не означает автоматическое выставление итогового результата.
Веса могут использоваться для расчёта показателей по критериям, отчёта и статистики.
Вопрос:

* Как именно должен использоваться вес варианта в отчёте и статистике?

7.6. Одиночный выбор
Одиночный выбор - критерий, в котором проверяющий выбирает один вариант ответа.
Для отчёта по такому критерию нужно показывать распределение ответов.
Комментарий Максима:
Для ОИМ и МИМ нужна гистограмма с объёмом выбора того или иного результата.
Фиксируем:

* для одиночного выбора в отчёте должна отображаться гистограмма;
* гистограмма показывает, сколько проверяющих выбрали каждый вариант.

7.7. Множественный выбор
Множественный выбор - критерий, в котором проверяющий может выбрать несколько вариантов.
Фиксируем:

* для множественного выбора в отчёте должна отображаться гистограмма;
* гистограмма показывает количество выборов по каждому варианту.

7.8. Текстовое поле
Текстовое поле используется для комментариев и качественной обратной связи.
По текстовым критериям не считаем среднее значение.
Комментарий Максима:
Комментарии текстом просто отразить в отчётике.
Фиксируем:

* текстовые ответы выводятся в отчёте;
* отдельный сложный интерфейс для анализа текстовых комментариев на первом этапе не требуется.

8. Статусная модель
8.1. Что было в исходном ТЗ
В исходном ТЗ были упомянуты:

* статус проверки работы для слушателя;
* статус назначенных на проверку работ для слушателя-проверяющего;
* факт отправки работы;
* факт заполнения формы проверки;
* факт отображения результата.

Предлагаемая статусная модель:
8.2. Статусная модель работы слушателя
Для работы, которую сдал слушатель, предлагается использовать следующие статусы.
1. Не сдано
Слушатель ещё не отправил работу.
2. Сдано
Слушатель отправил работу, но процесс взаимопроверки ещё не начался или работа ещё не назначена проверяющим.
3. На взаимопроверке
Работа назначена слушателям-проверяющим и/или проверяющим.
4. Взаимопроверка завершена, ожидает итогового результата
По работе собрано необходимое количество проверок.
На этом этапе слушатели-проверяющие больше не проверяют работу.
Итоговый результат ещё не выставлен.
5. Итоговый результат выставлен
Проверяющий с правом итогового решения выставил итоговый результат.
После этого слушатель, сдавший работу, видит итоговый результат по своей работе.
6. Возвращено на доработку
Работа возвращена слушателю на доработку.
Этот статус используется только если включена настройка возврата на доработку.
8.3. Статусная модель проверки, назначенной проверяющему
Для проверки, назначенной слушателю или проверяющему, предлагается использовать следующие статусы.
1. Назначена
Проверка назначена, но пользователь ещё не начал заполнять форму.
2. В работе
Проверяющий начал проверку, но ещё не отправил форму.
3. Проверена
Проверяющий отправил форму оценки.
4. Приостановлена
Проверка приостановлена, например, если работа была возвращена на доработку одним из проверяющих.
5. Отменена
Проверка больше не требуется или была снята с пользователя.

9. Возврат на доработку
В обычном ПЗ есть сценарий возврата работы на доработку.
Для P2P этот сценарий нужно сделать настраиваемым.
Комментарий Максима:
Я бы сделал настройкой. Если нет - то не может вернуть. Если да - то при возврате одним из проверяющих у всех приостанавливается проверка.
Фиксируем:

* возврат на доработку должен быть настройкой;
* если настройка выключена, вернуть работу на доработку нельзя;
* если настройка включена, проверяющий может вернуть работу на доработку;
* при возврате одним проверяющим проверка этой работы приостанавливается у всех остальных проверяющих;
* после повторной отправки работы нужно определить дальнейшую механику.

Вопрос:

* После повторной сдачи работы должен запускаться новый цикл взаимопроверки?
* Должна ли система сбрасывать предыдущие проверки?
* Или предыдущие проверки должны сохраняться в истории?

10. Кто участвует в проверке
Взаимопроверка должна поддерживать несколько типов проверяющих.
10.1. Слушатель потока
Слушатель потока может проверять работы других слушателей этого же потока.
Фиксируем:

* P2P работает только в рамках потока;
* слушатели выбираются из конкретного потока;
* слушатель не должен проверять свою работу;
* количество работ для проверки задаётся в настройках ПЗ внутри потока;
* слушатель-проверяющий заполняет критерии, но не выставляет итоговый зачёт / незачёт.

10.2. Проверяющий из настроек ПЗ

Он может:

* видеть работы;
* видеть результаты проверок;
* видеть отчётность;
* проверять работы;
* выставлять итоговый результат, если у него включена соответствующая настройка.

10.3. Неавторизованный пользователь по ссылке
Неавторизованный пользователь может проверить работу только по ссылке.
Он видит:

* саму работу;
* форму критериев.

Он не видит:

* личный кабинет;
* список других работ;
* статистику;
* результаты других проверяющих;
* итоговый результат;
* отчёт.

Логику личного кабинета для внешнего пользователя не реализуем.
10.4. Преподаватель
Преподаватель выделяется отдельной ролью для отображения и обсуждения.

11. Отчёт и статистика
По результатам взаимопроверки должен формироваться отчёт.
Комментарий Максима:
Я бы не делал интерфейс. Скорее отчёт PDF/Word - как в АОС. С возможностью скачать и на внешке, и в админке.
Фиксируем:

* отдельный сложный интерфейс статистики на первом этапе не делаем;
* формируем отчёт в формате PDF/Word;
* отчёт можно скачать во внешнем интерфейсе и в админке;
* отчёт относится к конкретному назначению ПЗ в поток, а не только к базовой карточке ПЗ.

11.1. Где скачать отчёт
Предлагаемая логика:

* во внешнем интерфейсе проверяющий видит отчёт или доступную ему часть отчёта по своей работе;
* в админке отчёт доступен в интерфейсе проверки ПЗ, назначенного в поток;
* также в интерфейсе потока должна быть возможность скачать отчёт.

11.2. Предварительный состав отчёта
Ниже предварительный состав отчёта. Его нужно подтвердить.
Отчёт может включать:

* название ПЗ;
* поток;
* слушателя, чья работа проверялась;
* статус работы;
* количество назначенных проверок;
* количество выполненных проверок;
* список проверяющих;
* результаты по шкальным критериям;
* гистограммы по критериям одиночного выбора;
* гистограммы по критериям множественного выбора;
* текстовые комментарии проверяющих;
* итоговый результат, если он выставлен;
* проверяющего, который выставил итоговый результат;
* дату выставления итогового результата.

12. Статистика во внешнем интерфейсе
12.1. Для слушателя, чью работу проверяют
Слушатель, который сдал работу, может видеть:

* статус своей работы;
* факт завершения взаимопроверки;
* итоговый результат, если он выставлен;
* доступные результаты по критериям;
* отчёт по своей работе, если скачивание отчёта разрешено.

Фиксируем:

* слушатель, сдавший работу, видит итоговый результат по своей работе после его выставления.

12.2. Для слушателя, который проверяет чужие работы
Слушатель-проверяющий может видеть:

* список назначенных ему работ;
* статус каждой назначенной проверки;
* свои отправленные оценки по критериям;
* оценки по уже проверенным работам, если это разрешено логикой продукта.

Комментарий Максима:
Оценки по уже проверенным работам.
Фиксируем:

* слушатель-проверяющий видит результаты по тем работам, которые он уже проверил.

Вопрос:

* Слушатель-проверяющий видит только свои оценки по чужой работе или также итоговый результат по этой чужой работе?

12.3. Для неавторизованного пользователя
Неавторизованный пользователь не видит статистику.
После отправки формы проверки ему не показываются:

* результаты других проверяющих;
* итоговый результат;
* статистика;
* отчёт.

13. Уведомления
Система должна уведомлять слушателей потока о доступных работах для проверки через пользовательский интерфейс.
Для слушателей потока уведомления возможны внутри системы, потому что они авторизованы и находятся в потоке.
Для внешних неавторизованных пользователей уведомления остаются открытым вопросом.
Проблема:

* внешний пользователь проходит по ссылке;
* у него может не быть личного кабинета;
* непонятно, куда отправлять уведомление, если у системы нет его email или другого контакта.

Комментарий Максима:
Давай на усмотрение менеджера / админа.
Фиксируем вопросом:

* Как менеджер / администратор должен отправлять уведомления внешним пользователям?
* Или внешние пользователи не получают уведомления, а ссылка передаётся им вне системы?

Предлагаемая логика для первого этапа:

* уведомления делаем только для авторизованных слушателей потока;
* внешним пользователям уведомления не отправляем;
* если нужна внешняя проверка, ссылка передаётся вручную вне системы.

14. Сертификаты
Сертификаты могут выдаваться:

2. за выполнение проверки.

Фиксируем:

* сертификат может выдаваться за выполнение проверки;

14.1. Сертификат за проверку
Комментарий Максима:

* если слушателю назначено проверить N работ, сертификат за проверку выдаётся после проверки всех N работ.

14.2. Внешние пользователи
Вопрос про внешних пользователей не подтверждён.

17.2. Значимые уточнения, которые нужно проверить на наличие в смете или досметить
Ниже перечислены требования и уточнения, которые появились или были существенно конкретизированы после проработки ТЗ и комментариев Максима. Их нужно отдельно проверить в смете.

1. Разделение настроек между карточкой ПЗ и настройками ПЗ в потоке.
В кратком ТЗ указано, что функциональность должна быть отдельной настройкой для активности типа «Практическое задание», но не было детально разделено, что настраивается в базовой карточке ПЗ, а что - при назначении ПЗ в конкретный поток.
2. Настройка количества работ, которые должен проверить каждый слушатель.
В кратком ТЗ указана проверка слушателями потока, но отдельно не описана настройка количества работ на одного слушателя.
3. Правило исключения собственной работы из проверки.
Для P2P нужно явно реализовать правило: слушатель не должен получать на проверку собственную работу.
4. Проверяющий с правом выставления итогового результата.
В кратком ТЗ указано, что слушатель должен получать итоговую оценку, но не описано, кто именно её выставляет.
После уточнения фиксируем: итоговый результат выставляет не система автоматически, а проверяющий с правом итогового решения.
5. Отдельный статус “Взаимопроверка завершена, ожидает итогового результата”.
В кратком ТЗ не описана статусная модель.
После уточнения нужно разделить два состояния:
   * взаимопроверка завершена, нужное количество проверок собрано;
   * итоговый результат выставлен проверяющим.
6. Статусная модель работы и назначенных проверок.
Нужно описать и реализовать статусы работы слушателя и статусы проверки, назначенной проверяющему / слушателю-проверяющему.
7. Настраиваемая шкала с вариантами и весами.
В кратком ТЗ есть индивидуальные критерии, но не было требования про настраиваемую шкалу и веса вариантов.
Это появилось после комментария Максима.
8. Гистограммы по одиночному и множественному выбору в отчёте.
Это новое уточнение, ранее не описанное в кратком ТЗ.
Гистограмма должна отображаться в PDF/Word-отчёте и показывать, сколько проверяющих выбрали каждый вариант ответа.
9. PDF/Word-отчёт по результатам взаимопроверки.
В кратком ТЗ указана разработка или доработка отчёта, но формат PDF/Word и логика скачивания отчёта были уточнены позже.
Нужно проверить, был ли такой формат уже заложен в смету.
10. Возврат работы на доработку при взаимопроверке.

В кратком ТЗ этот сценарий не описан.
После комментария Максима появилась логика: возврат должен быть настройкой, а при возврате одним проверяющим проверка приостанавливается у всех.

11. Сертификат за выполнение всего назначенного объёма проверок.

В кратком ТЗ есть выдача сертификата за проведённую оценку.
После уточнения фиксируем конкретное условие: сертификат за проверку выдаётся после выполнения всех назначенных проверок в рамках одного ПЗ, а не за одну отдельную проверку.

12. Уведомления сторонних пользователей.

В кратком ТЗ указано уведомление сторонних пользователей по иным каналам связи, но механизм не раскрыт.
Нужно отдельно определить: система сама отправляет уведомления внешним пользователям или менеджер передаёт ссылку вручную вне системы.
Если система должна отправлять уведомления внешним пользователям сама, это значимая доработка.

18. Краткая итоговая схема

1. В карточке ПЗ включается режим взаимопроверки.
2. В карточке ПЗ выбираются проверяющие.
3. У одного или нескольких проверяющих может быть включено право выставления итогового результата.
4. В карточке ПЗ настраиваются критерии оценки.
5. При назначении ПЗ в поток задаётся количество работ, которое должен проверить каждый слушатель.
6. Слушатели потока сдают работы.
7. Система распределяет работы между слушателями для проверки.
8. Слушатель не получает на проверку собственную работу.
9. Слушатели-проверяющие заполняют форму критериев.
10. Система собирает результаты проверок.
11. После набора нужного количества проверок работа переходит в статус «Взаимопроверка завершена, ожидает итогового результата».
12. Проверяющий с правом итогового результата смотрит результаты проверок.
13. Проверяющий выставляет итоговый результат.
14. Работа переходит в статус «Итоговый результат выставлен».
15. Слушатель, сдавший работу, видит итоговый результат по своей работе.
16. Формируется PDF/Word отчёт.
17. Сертификат за проверку выдаётся после выполнения всего назначенного объёма проверок в рамках одного ПЗ.
