# Разведка: опрос в потоке + неавторизованный доступ, сертификат слушателя (develop, 15.10.2026)

Для черновиков TC-E2E-038/039 из `docs/test_cases/e2e.md`. k8s выведен из эксплуатации
(владелец, 15.10.2026) — разведка и дальнейшая автоматизация переносятся на develop
(стенд подтверждён живым с 14.10 вечера). Скрипты: `scripts/_recon_poll_stream.py`,
`scripts/_recon_certificate_listener.py` (не часть прогона, оставлены для повторного
использования).

## Опрос в потоке + неавторизованная попытка (TC-E2E-038) — разведано полностью

- **Создание и назначение в поток**: тот же API-рецепт, что уже есть в
  `tests/api/e2e/test_e2e_content_to_module.py::test_e2e_poll_to_module` — `PollsEndpoint.create`
  (обложка через `TincanEndpoint.upload_cover`) → вопросы `create_question` → назначение в
  модуль `AssignmentsEndpoint.assign_content_to_module`.
- **UI слушателя**: тот же путь, что у теста в потоке
  (`tests/ui/tests/stream/test_user_test_stream_flow.py`) — логин → онбординг внутри
  программы (`UserSidebarPage.pass_onboarding()`) → вкладка «Курсы и тесты» → карточка по
  имени (`name_client` или `name`). Только что назначенный контент иногда не виден сразу —
  один reload+retry обычно хватает (индексация, тот же эффект, что уже задокументирован для
  тестов).
- **Запуск плеера**: клик «Начать» открывает плеер в НОВОЙ вкладке (как у инд. опроса,
  `tests/ui/polls/individual/test_poll_flow.py`), URL вида
  `/testing/player/{content_id}/{assignment_uuid}`.
- **Неавторизованный доступ — ключевой результат**: та же ссылка плеера в браузерном
  контексте без куки сессии → редирект на
  `/auth/main?uri-callback=%2Ftesting%2Fplayer%2F{content_id}%2F{uuid}` (обычная форма
  логина с колбэком). В отличие от АОС (`tests/ui/aos/user/test_aos_public_link.py`,
  `AosEndpoint.public_link` — отдельный backend-эндпоинт публичной ссылки), у опроса в
  потоке анонимного/публичного доступа к плееру НЕТ — это ожидаемое поведение, не дефект:
  публичная ссылка подтверждена как отдельная фича именно АОС, опрос её не предоставляет.
- Прогона теста на самом опросе (ответы на вопросы) не делал — сценарий такой же, как уже
  покрыт в `test_ui_poll_flow` (инд. трек), автоматизация может переиспользовать те же шаги
  взаимодействия с плеером.

**В кейс (TC-E2E-038) можно класть как есть**: API — программа → поток → модуль, назначить
слушателя на поток, создать опрос с вопросами, назначить в модуль; UI — слушатель находит
и проходит опрос на вкладке «Курсы и тесты» (как `test_user_test_stream_flow`/`test_ui_poll_flow`
вместе); скопировать URL плеера; тот же URL без сессии → редирект на `/auth` с
`uri-callback` — это ожидаемое поведение, не xfail/баг.

## Сертификат слушателя программы (TC-E2E-039) — разведано частично, есть открытый вопрос

Подготовка прошла чисто и подтверждена логами (develop, 15.10.2026, 3 независимых прогона):
программа → поток → модуль → курс Tincan (`created_tincan`) → `assign_to_module` →
`modules_endpoint.find_stream_content_id` → `CertificatesEndpoint.create_template`
(`template_type="program_stream"`, файл через `TincanEndpoint.upload_certificate_file`) →
`assign_template(template_id, [stream["attributes"]["content_id"]])` (ответ `{"result": true}`
каждый раз) → пользователь назначен на поток.

**Открытый вопрос**: `AssignmentsEndpoint.change_state(..., state=CONTENT_STATE_PASSED)` на
этом сценарии НЕ дал состояние «пройдено» — ни сразу, ни через 3с/10с (`list_for_stream`
стабильно возвращает `state: 0, status: "Назначено"`), ни по дашборду курса
(`DashboardsEndpoint.wait_for_course_row`, 30с ожидания — `passed: 0, not_started: 1`),
хотя сам вызов `change_state` отвечает `{"status": "success"}` без ошибки. При этом **тот же
самый механизм подтверждённо работает** — немодифицированный
`tests/ui/learning_statistics/test_courses_table_progress.py::test_status_passed_updates_after_change_state`
прогнан отдельно сразу после и прошёл штатно (develop, 15.10.2026). То есть это не
регрессия стенда и не баг change_state как такового — разница в чём-то специфичном для
сценария сертификата (возможно, во взаимодействии с уже назначенным на поток шаблоном
сертификата, не проверялось изолированно), не выяснено за три повтора.

**Из-за этого слушательская часть (видимость/скачивание сертификата) осталась
неподтверждённой**: при «непройденном» (по данным API) курсе сертификат закономерно нигде
не нашёлся — ни на главной «Моё обучение» (карточка программы показывает «Программа
закончилась» + кнопку «Оценить», не «Пройдено»), ни в деталях программы
(`/education/program/{uuid}/module/{id}`), ни в выпадающем меню пользователя (там только
«Мой профиль», «QR-код», «Выйти» — пункта с сертификатами нет), ни на `/profile` (404 —
не реальный маршрут слушателя), ни по слову «сертификат» в тексте `/education`.

**Не проверено в этом раунде** (следующий шаг, если возвращаться к этому кейсу):
1. Изолированный повтор того же `change_state` БЕЗ предварительного назначения шаблона
   сертификата на поток — чтобы понять, влияет ли сам факт привязанного сертификата на
   переход в «пройдено», или дело в чём-то ещё.
2. Админский просмотр — карточка пользователя в админке имеет вкладку «Сертификаты»
   (упомянута в `docs/e2e/offline_events_recon.md` в перечне вкладок карточки, сама вкладка
   не открывалась) — не проверялось, появляется ли там что-то даже при текущем «непройденном»
   статусе или только после настоящего «Пройдено».
3. «Мой профиль» в выпадающем меню — клик не менял URL в этом прогоне (возможно модалка,
   которая не успела открыться / неверный селектор `.v-overlay--active a:has-text(...)`) —
   содержимое модалки не увидено, может содержать раздел с сертификатами.
