# Разведка: опрос в потоке + неавторизованный доступ, сертификат слушателя (develop, 15.10.2026)

Для черновиков TC-E2E-038/039 из `docs/test_cases/e2e.md`. k8s выведен из эксплуатации
(владелец, 15.10.2026) — разведка и дальнейшая автоматизация переносятся на develop
(стенд подтверждён живым с 14.10 вечера). Скрипты: `scripts/_recon_poll_stream.py`,
`scripts/_recon_certificate_listener.py` (не часть прогона, оставлены для повторного
использования).

## Опрос в потоке + неавторизованная попытка (TC-E2E-038) — разведано полностью

- **Создание и назначение в поток**: тот же API-рецепт, что уже есть в
  `tests/api/e2e/test_e2e_content_to_module.py::test_e2e_poll_to_module` — `PollsEndpoint.create`
  (обложка через `TincanEndpoint.upload_cover`) → вопросы `create_question` → назначение в
  модуль `AssignmentsEndpoint.assign_content_to_module`.
- **UI слушателя**: тот же путь, что у теста в потоке
  (`tests/ui/tests/stream/test_user_test_stream_flow.py`) — логин → онбординг внутри
  программы (`UserSidebarPage.pass_onboarding()`) → вкладка «Курсы и тесты» → карточка по
  имени (`name_client` или `name`). Только что назначенный контент иногда не виден сразу —
  один reload+retry обычно хватает (индексация, тот же эффект, что уже задокументирован для
  тестов).
- **Запуск плеера**: клик «Начать» открывает плеер в НОВОЙ вкладке (как у инд. опроса,
  `tests/ui/polls/individual/test_poll_flow.py`), URL вида
  `/testing/player/{content_id}/{assignment_uuid}`.
- **Неавторизованный доступ — ключевой результат**: та же ссылка плеера в браузерном
  контексте без куки сессии → редирект на
  `/auth/main?uri-callback=%2Ftesting%2Fplayer%2F{content_id}%2F{uuid}` (обычная форма
  логина с колбэком). В отличие от АОС (`tests/ui/aos/user/test_aos_public_link.py`,
  `AosEndpoint.public_link` — отдельный backend-эндпоинт публичной ссылки), у опроса в
  потоке анонимного/публичного доступа к плееру НЕТ — это ожидаемое поведение, не дефект:
  публичная ссылка подтверждена как отдельная фича именно АОС, опрос её не предоставляет.
- Прогона теста на самом опросе (ответы на вопросы) не делал — сценарий такой же, как уже
  покрыт в `test_ui_poll_flow` (инд. трек), автоматизация может переиспользовать те же шаги
  взаимодействия с плеером.

**В кейс (TC-E2E-038) можно класть как есть**: API — программа → поток → модуль, назначить
слушателя на поток, создать опрос с вопросами, назначить в модуль; UI — слушатель находит
и проходит опрос на вкладке «Курсы и тесты» (как `test_user_test_stream_flow`/`test_ui_poll_flow`
вместе); скопировать URL плеера; тот же URL без сессии → редирект на `/auth` с
`uri-callback` — это ожидаемое поведение, не xfail/баг.

## Сертификат слушателя программы (TC-E2E-039) — где смотреть найдено, начисление не воспроизведено

Подготовка прошла чисто и подтверждена логами (develop, 15.10.2026, 4 независимых прогона):
программа → поток → модуль → курс Tincan (`created_tincan`) → `assign_to_module` →
`modules_endpoint.find_stream_content_id` → `CertificatesEndpoint.create_template`
(`template_type="program_stream"`, файл через `TincanEndpoint.upload_certificate_file`) →
`assign_template(template_id, [stream["attributes"]["content_id"]])` (ответ `{"result": true}`
каждый раз) → пользователь назначен на поток.

**Где слушатель видит сертификат (подтверждено владельцем + разведкой)**: вкладка
«Мои сертификаты» на `/profile/{user_id}` (`scripts/_recon_profile_cert_tab.py`) — на
странице три вкладки: «Профиль», «Мои сертификаты», «Документы о квалификации». Структура
подтверждена скриншотом; для пользователя без начисленных сертификатов вкладка пуста, сетевой
запрос по клику с подстрокой `certificat` в URL не пойман (возможно, данные уже в составе
первого запроса страницы, а не отдельным вызовом по клику — не выяснено). По словам
владельца, сертификат также приходит уведомлением, начисляется при завершении активности
с привязанным сертификатом ИЛИ при завершении программы целиком. Ранее проверенные
«Мой профиль» в выпадающем меню (ссылка `href="/profile/{id}"`, клик по которой не переходил
в этом прогоне — вероятно, меню закрывалось раньше клика) и `/profile` без id (404) были
тупиковыми путями; правильный маршрут — именно `/profile/{id}`.

**Не удалось воспроизвести живым прогоном — назначение не перешло в «пройдено»**: за 4
попытки `AssignmentsEndpoint.change_state(..., state=CONTENT_STATE_PASSED)` ни разу не дал
состояние «пройдено» ни по `list_for_stream` (стабильно `state: 0, status: "Назначено"`), ни
по дашборду курса (`DashboardsEndpoint.wait_for_course_row`) — включая повтор с тем же
таймаутом 60с, что использует проверенный
`test_courses_table_progress.py::test_status_passed_updates_after_change_state` (тот прогнан
отдельно в тот же день и прошёл штатно). Изолированная проверка сняла подозрение на
сертификат как причину: тот же дашборд-запрос БЕЗ какого-либо шаблона сертификата один раз
вообще не нашёл строку курса в статистике за 90с (`wait_for_course_row` без предиката,
просто на существование строки) — то есть сам поиск курса в `/api/v1/statistics/courses`
по имени+потоку периодически либо сильно запаздывает, либо требует большего времени, чем
60-90с, независимо от сертификатов. Это согласуется с уже задокументированным в том же файле
паттерном лага статистики на develop (см. упоминание 120-секундного лага для другого поля) —
похоже, границы лага шире, чем документированные ~2с для конкретно этого курсового счётчика.

**Открыто для возврата**:
1. Автоматизации TC-E2E-039 нужен более надёжный сигнал «пройдено» для стрима/курса, чем
   `wait_for_course_row` с таймаутом в районе минуты — либо ретраить с 120с+, либо найти
   более быстрый/прямой источник статуса.
2. Сам факт начисления сертификата (после того как «пройдено» подтвердится) — не
   воспроизведён; шаги 3-4 кейса (вид сертификата в «Мои сертификаты», скачивание файла)
   проверены только структурно (пустая вкладка), не с реальным сертификатом.
3. Админская вкладка «Сертификаты» в карточке пользователя (упомянута в
   `docs/e2e/offline_events_recon.md`) по-прежнему не открывалась.
