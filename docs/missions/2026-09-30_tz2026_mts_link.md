# Миссия: интеграция с МТС Линк — план тестирования, тест-кейсы, каркас автотестов (до разработки)

Записано 30.09.2026 по решению владельца. Разработки, ветки и токена МТС Линк **нет** — это этап
планирования. Задача миссии: когда появится ветка, у QA уже есть план, кейсы в test_hub и каркас
автотестов, который включается одним флагом.

Источник требований: `docs/requirements/tz2026/README.md` (каталог с актуальностью) и
`docs/requirements/tz2026/mts_link/*.md`. Прочитать README целиком до начала — там правила
приоритета версий и известные расхождения. Основа — части 0–14 (`10_…` – `25_…`), проработка
01.07 (`04_…`) — там, где части молчат, ТЗ 4.1 (`01_…`) — для трассировки требований.

## Правила (обязательны)

- Стенды: **ничего не запускать** против develop/stage/prod в рамках новых тестов — функционала нет.
  Разрешена только разведка **на чтение** на `--env develop` через существующие фикстуры:
  посмотреть текущую карточку очного мероприятия в админке (тип, поля, URL мероприятия), таблицу
  слушателей потока (ячейки посещения), карточку тенанта, «Результаты активности» на внешке —
  чтобы page objects и кейсы опирались на реальные поля и селекторы. Данные не создавать.
- Учётки только из `.env` через `config/environments.py`; значения в код/логи/коммиты не писать.
- Структура проекта: клиенты `api/endpoints/<area>.py`, page objects `ui/pages/`, тесты
  `tests/api/mts_link/`, `tests/ui/mts_link/`, маркеры `api`/`ui` + новый маркер `mts_link`
  (зарегистрировать в `pytest.ini`), allure `@allure.feature("Интеграция МТС Линк")`,
  `@allure.story(<часть N>)`, `@allure.title` на русском, docstring с предусловиями.
- Кейсы — в папке `docs/test_cases/mts_link/`, по файлу на часть, формат `docs/test_cases/TEMPLATE.md`
  (см. этап 1). **Порядок этапов: сначала кейсы (этап 1), потом план (этап 2), потом каркас (этап 3)** —
  владелец хочет видеть кейсы первыми.
- Коммиты небольшие, на русском. `README.md`: раздел «Интеграция МТС Линк (в ожидании ветки)».
- Не менять существующие тесты и page objects, кроме точечных расширений (см. этап 3).

## Этап 1. Тест-кейсы — папка `docs/test_cases/mts_link/`

Один файл на часть: `00_tenant_settings.md` (часть 0.1), `01_event_type.md` (часть 0), `02_create.md`,
`03_update.md`, `04_participants.md`, `05_lecturers.md`, `06_files.md`, `07_delete.md`, `08_statuses.md`,
`09_retry.md`, `10_attendance.md`, `11_logging.md`, `12_recording.md`, `13_trajectory.md`,
`14_dev_real_e2e.md` (часть 13), `15_regression.md`. Шапка каждого файла — как в TEMPLATE, в поле
«Область» — номер части и файл требований. test_hub читает эту папку рекурсивно (задача в test_hub
заведена параллельно), ручные кейсы без строки `- Автотест:` тоже импортируются.

Формат `TEMPLATE.md`: шапка, `### TC-MTS-NNN <название>`, строки `- Автотест:` (nodeid из этапа 3
для автоматизируемых — nodeid придумать сразу здесь по схеме `tests/api/mts_link/test_<часть>.py::Test<Часть>::test_<что>`,
этап 3 обязан его повторить; для ручных строку **не писать**), `- Приоритет/Тип/Роли`, `- Предусловия`,
добавить строку `- Требование: часть N, п. …` (test_hub её проигнорирует, генератор не трогает),
таблица шагов «Действие / Ожидаемый результат». Нумерация сплошная, группы по частям:

- Часть 0.1 тенант: сохранение с валидным токеном (признак интеграции появился), невалидный токен
  (не сохраняется, понятная ошибка), МТС недоступен, маска токена в ответе, «поле не трогали —
  токен прежний», замена целиком, права (администратор, администратор тенанта; менеджер — нет).
- Часть 0 тип: иконка типа при настроенной интеграции, скрыта без неё, URL недоступен, тип не
  меняется в обе стороны, статусы в результатах активности, отключение интеграции — старые живут.
- Часть 1 создание: мероприятие создано сразу, статус «в процессе» → «успешно», сохранены id
  вебинара/сессии/ссылка, URL подставлен; ошибка: мероприятие остаётся, URL пуст, ретрай, части 2–5
  не стартуют.
- Часть 2 обновление: изменение полей, уходящих в МТС → синхронизация; только внутренних → нет
  запроса (проверять по `request_log_audit`); после начала вебинара поля заблокированы; ошибка —
  данные в ЛМС остаются, статус ошибки, ретрай.
- Часть 3 участники: первичная регистрация всех, добавили → зарегистрирован с персональной
  ссылкой, убрали до вебинара → удалён + софт-делит, убрали после → регистрация не тронута,
  ошибка по одному не блокирует остальных, повторная сверка добивает.
- Часть 4 лекторы: аналогично, роль ведущего, независимость от участников/файлов.
- Часть 5 файлы: добавили/заменили/удалили, проверка формата и размера до отправки с указанием
  файла, остальные грузятся, по одному за раз, ошибка по одному не блокирует.
- Часть 6 удаление: удаляется сразу в ЛМС, фоном вебинар + сессия, ошибка — ретрай, «висящих» нет.
- Часть 7 статусы: сводный статус (любая ошибка → ошибка мероприятия), индикаторы в списке и
  календаре, детализация по пяти частям в карточке, пуш создателю один раз на факт ошибки, а не на
  каждый ретрай, переход из пуша в карточку.
- Часть 8 ручной перезапуск: кнопка только при ошибке, перезапуск части, перезапуск создания тянет
  всю цепочку, при идущем авторетрае повторный запуск не создаётся.
- Часть 9 процент: формула по фактической длительности, целые проценты, ≥75 % галка, <75 %
  процент, 0 % не был, пусто до статистики, обычные мероприятия без изменений, по каждому
  вебинару отдельно.
- Часть 10 логи: смена настроек тенанта (факт смены токена без значения), создание/изменение/
  удаление мероприятия с признаком синхронизации, все запросы/ответы в `request_log_audit` по
  операциям, маскирование токена в теле.
- Часть 11 запись: плеер в результатах активности, досмотр до конца → посещение засчитано только
  если очно не засчитано; уже засчитано очно → ничего не меняется.
- Часть 14 траектория: вебинар на каждое назначение, один участник, снятие назначения до
  вебинара → удаление целиком, после → не удаляем.
- Часть 13 как e2e-чек-лист на dev с реальным аккаунтом: 9 шагов цикла + 4 ошибочных сценария —
  ручные кейсы (без автотеста), уровень dev-real.
- Регресс: обычное очное мероприятие создаётся/редактируется как раньше; таблица слушателей для
  обычных мероприятий; тенант без интеграции.

Каждый кейс: приоритет по риску, роли, предусловие (сид из части 12, если есть). Ожидаемые
результаты формулировать проверяемо (какой статус, какое поле, какая запись в логе).

## Этап 2. План тестирования — `docs/plans/2026-09-30_tz2026_mts_link_test_plan.md`

Документ для владельца (QA), читают аналитик и разработчики. Разделы:

1. **Объект и границы.** Что тестируем (части 0–14 списком с одной фразой на часть), что не
   тестируем (внутренности МТС Линк, реальные письма МТС, конвертация записи на их стороне).
2. **Стратегия по уровням.** (а) Локально/на ветке с моками и сидами — часть 12 — основной объём:
   статусы, ретраи, ручной перезапуск, ошибки (невалидный токен, недоступность, отказ по объекту,
   файл сверх лимита); (б) dev с реальным аккаунтом — часть 13 — сквозной цикл и сверка моков с
   реальностью; (в) регресс существующего: обычные мероприятия, таблица слушателей, результаты
   деятельности не должны измениться (часть 9 «что не меняется»).
3. **Матрица трассировки.** Таблица: требование (часть N / пункт ТЗ 4.1.x) → проверки (ID кейсов
   TC-MTS-… из этапа 1) → уровень (mock / dev-real / регресс) → автотест (да/план/ручной). Требования 4.1.2.3
   (алгоритмы синхронизации УЗ: есть там/нет тут и наоборот, различие атрибутов) и 4.1.3.2 (SSO)
   в частях 0–14 не покрыты — отдельная строка «требование ТЗ не имеет реализации в постановке»
   с вопросом.
4. **Тестовые данные и окружение.** Что нужно от разработки, чтобы тесты были возможны:
   переключение мок/реальный клиент через env стенда; управляемые ответы мока (как заставить мок
   вернуть 401/503/отказ по объекту — эндпоинт, заголовок, сид?); сиды из части 12; доступ к
   `request_log_audit` (SQL или API); способ дождаться фоновой синхронизации (поллинг статуса,
   таймаут ретраев); тестовый тенант с интеграцией и без; учётки admin/tenant-admin/manager/
   teacher/learner. Оформить как список вопросов разработчикам с предлагаемым ответом.
5. **Риски.** Асинхронность и ретраи (флаки тестов по времени), одна сессия на вебинар, софт-делит
   участников после вебинара, порог 75 % и «фактическая длительность из МТС», индивидуальная
   траектория (вебинар на назначение), отключение интеграции при живых мероприятиях, маскирование
   токена, ограничение редактирования после начала.
6. **Открытые вопросы** аналитику/заказчику — свести из README (расхождения 01.07 vs части) и
   из чтения частей; каждый с номером, к какой части относится и что блокирует.
7. **Критерии.** Готовность к тестированию (ветка + моки + сиды + ответы на блокирующие вопросы);
   критерии приёмки (все high-кейсы пройдены на моках, сквозной цикл на dev по части 13 пройден,
   ошибочные сценарии части 13 пройдены, регресс зелёный).
8. **Оценка объёма**: количество кейсов по частям и уровням, сколько автоматизируем.

## Этап 3. Каркас автотестов (включается флагом, пока skip)

- `config/environments.py`/`.env.example`: флаг `MTS_LINK_READY` (по умолчанию пусто) и
  `MTS_LINK_TENANT_ID`, `MTS_LINK_MOCK_MODE`-подобные переменные — только те, что реально нужны.
  В `tests/api/mts_link/conftest.py` и `tests/ui/mts_link/conftest.py` фикстура автоиспользования:
  если флаг не выставлен → `pytest.skip("Интеграция МТС Линк: ветки нет (миссия 30.09.2026)")`.
  `--collect-only` показывает все тесты, прогон без флага даёт аккуратные skip.
- `api/endpoints/mts_link.py`: клиент с **предполагаемыми** эндпоинтами, каждый метод с docstring
  «контракт не подтверждён, часть N» — настройки тенанта (GET/PUT), создание мероприятия типа
  «МТС Линк» (через существующие `schedule_items.py`, посмотреть, как создаются очные
  мероприятия сейчас), статус интеграции мероприятия, ручной перезапуск, процент посещения в
  таблице слушателей, выборка `request_log_audit` (если API не будет — helper через SQL, как в
  `tests/api/buk` с `external_requests_audit`). Никаких выдуманных URL без пометки.
- Page objects: `ui/pages/admin_tenant_page.py` (блок МТС Линк: токен, сохранить, маска, ошибка),
  расширение `admin_programs_page.py`/`admin_activities_page.py` или новый
  `admin_event_mts_page.py` (иконка типа, URL disabled, блок статусов с пятью строками, кнопка
  «Повторить»), `ui/pages/stream_listeners_page.py` (ячейка посещения: галка/процент/пусто),
  `activity_page.py` (плеер записи). Селекторы — по разведке текущих экранов + `data-*`/текст
  для новых элементов, с комментарием «уточнить после появления ветки».
- Тесты: по одному на каждый кейс этапа 1, у которого указан `- Автотест:`; nodeid совпадает
  строго. Тело теста — реальные шаги под предполагаемый контракт, а не `pass`. Общие помощники:
  ожидание статуса синхронизации с таймаутом (поллинг), включение сценария ошибки мока (обёртка с
  TODO на способ, который даст разработка).
- `tests/product_map.yml`: узлы `adm_tenant_integration` («Тенант · МТС Линк»), `adm_event_mts`
  («Мероприятие МТС Линк»), `adm_stream_attendance` («Таблица слушателей · посещение»),
  `int_mts_link` в зоне интеграций (стрелка в админку и во внешку `ext_activity_results`), с
  префиксами `tests/api/mts_link`, `tests/ui/mts_link`. Не ломать раскладку: проверить, что
  координаты не пересекают соседей (зона `int` — y 670–840).
- Unit-проверка без стенда: `pytest --collect-only -q tests/api/mts_link tests/ui/mts_link`
  собирает все тесты; `pytest -q tests/api/mts_link tests/ui/mts_link --env develop` без флага —
  все skipped, ни одного failed/error; `python tools/test_cases/generate.py --check` (или как
  он проверяет) не ругается на файлы в `docs/test_cases/mts_link/`.
