# Миссия: взаимопроверка ПЗ (peer-to-peer) — тест-кейсы, план тестирования, каркас автотестов (до разработки)

Записано 30.09.2026 по решению владельца. Разработки и ветки **нет**, часть решений ещё не
подтверждена заказчиком (16 открытых вопросов). Задача миссии: кейсы, план и каркас, которые
пригодятся, когда появится ветка, с явной пометкой всего, что зависит от ответов заказчика.

Источник требований: `docs/requirements/tz2026/README.md` (правила приоритета версий: 04 → 03 → 02,
известные расхождения) и `docs/requirements/tz2026/p2p/*.md`. Читать README целиком до начала.
Парная миссия — `docs/missions/2026-09-30_tz2026_mts_link.md`: те же правила, тот же формат кейсов и
тот же порядок этапов (кейсы → план → каркас); здесь описаны только отличия.

## Правила (обязательны)

- Как в миссии МТС Линк: стенды не запускать, разведка на `--env develop` только на чтение —
  посмотреть текущую карточку ПЗ в базе активностей (поля, «Проверяющие», «Преподаватели»,
  «Система оценивания», «Сертификат»), назначение ПЗ в поток, интерфейс проверяющего
  (`ui/pages/reviewer_page.py`, `tests/ui/practical_tasks/test_review_practical_task.py`),
  прохождение ПЗ слушателем (`practical_task_page.py`), конструктор тестов
  (`test_constructor_admin_page.py` — критерии, судя по документам, будут строиться на нём).
  Существующие тесты ПЗ — образец структуры и селекторов, не менять.
- Маркер `p2p`, allure `@allure.feature("Взаимопроверка ПЗ")`, `@allure.story(<раздел>)`.
- Все спорные точки (см. README) — не выбирать вариант молча: кейс пишется по приоритетной
  версии (04), а в предусловии строка `Ждёт ответа заказчика: вопрос №N (05_вопросы…)`;
  в плане такие кейсы собраны в отдельную таблицу «зависят от решений».

## Этап 1. Тест-кейсы — папка `docs/test_cases/p2p/`

Файлы: `00_pt_card_settings.md` (карточка ПЗ: тумблер взаимопроверки, блокировка после первой
сданной работы, штатные проверяющие, автоназначение роли «Преподаватель»), `01_criteria.md`
(конструктор критериев: шкала/ОиМ/МиМ/текст, запрет добавлять/удалять после первой проверки,
правка текста разрешена, шаблон по умолчанию — вопрос), `02_stream_settings.md` (в потоке:
участники, ручной/авто режим, «работ на слушателя», минимум проверок на работу, сроки),
`03_distribution.md` (ручное назначение, своя работа не назначается, авто-распределение,
лимиты, закрытие после минимума — вопрос), `04_peer_review.md` (слушатель-проверяющий: список
только чужих, форма критериев, редактирование до финального подтверждения, блокировка после),
`05_external_reviewer.md` (внешний по ссылке: ФИО + опц. email, персональная ссылка, список
всех работ ПЗ в потоке, повторный вход, несколько внешних с одинаковым ФИО, нет ЛК/статистики,
срок и отзыв ссылки — вопрос), `06_final_result.md` (штатный проверяющий видит все peer-проверки
и агрегаты, выставляет/меняет итог; администратор без назначения не может; авто-итог без
штатных — вопрос), `07_aggregation.md` (среднее по числовым с округлением до 0,1, текстовые
списком, гистограммы ОиМ/МиМ в отчёте), `08_return_for_revision.md` (возврат штатным,
приостановка у остальных, повторная сдача → повторный цикл, видимость «доработано», хранение
старых результатов — вопрос), `09_statuses.md` (статусы работы и назначенной проверки по 03,
раздел 8), `10_author_view.md` (автор видит статус, итог, значения по критериям; анонимность —
вопрос), `11_report.md` (PDF/Word, состав, где скачать — вопросы), `12_notifications.md`
(UI-уведомления слушателям о назначенных работах; повторное после доработки — вопрос),
`13_certificates.md` (за весь назначенный объём проверок в ПЗ; внешние — нет), `14_roles_access.md`
(матрица ролей из 04 §3: кто что видит/может; групповые ПЗ — недоступно, из 02), `15_logging.md`
(перечень из 04 §15), `16_regression.md` (ПЗ с выключенной взаимопроверкой работает как раньше —
опереться на существующие тесты ПЗ; ограничение «одно ПЗ один раз в программе» не меняется).

ID `TC-P2P-NNN`, сквозная нумерация. Строка `- Требование: 04 §N` (или 03 §N / ТЗ 1.1.x.x).
Автотест планировать (строка `- Автотест:` с nodeid `tests/{api,ui}/p2p/test_<файл>.py::…`) для:
настроек карточки и потока (API), распределения и «своя работа не назначается» (API),
peer-проверки и внешней ссылки (UI + API), итога и агрегации (API), статусов, регресса.
Отчёт PDF/Word, уведомления, сертификаты, гистограммы — ручные.

## Этап 2. План тестирования — `docs/plans/2026-09-30_tz2026_p2p_test_plan.md`

Разделы как в плане МТС Линк, со своей спецификой:
- объект: разделы 1–16 документа 04 (+ статусная модель из 03 §8, типы критериев 03 §7);
- стратегия: основной объём — на ветке с реальными данными (внешних систем нет), сложность в
  многоролевых сценариях: нужны 3+ слушателя, штатный проверяющий, внешний, администратор —
  описать набор учёток и данных, которые тесты создают сами (префикс `Автотест_`);
- матрица трассировки: пункт краткого ТЗ (1.1.1.1–1.1.5.1, см. цитаты в 04 и сверку в 02) →
  кейсы → автотест;
- отдельная таблица «кейсы, зависящие от ответов заказчика» с номером вопроса из 05;
- расхождения версий 02/03/04 — как вопросы аналитику (уже перечислены в README, дополнить);
- риски: алгоритм авто-распределения не выбран, версии критериев после начала, повторный цикл
  после доработки, внешняя ссылка без авторизации (безопасность: перебор ссылок, доступ к чужим
  работам, повторная отправка), анонимность, производительность при N×M назначениях;
- критерии готовности и приёмки, оценка объёма.

## Этап 3. Каркас автотестов (skip по флагу `P2P_READY`)

- Флаг `P2P_READY` в `.env.example`/`config/environments.py`, conftest в `tests/api/p2p/` и
  `tests/ui/p2p/` со skip без флага.
- `api/endpoints/p2p.py`: предполагаемые методы поверх существующих `homework*.py`/
  `assignments.py`/`streams.py` (посмотреть, как сейчас создаётся ПЗ, назначается в поток, сдаётся и
  проверяется — переиспользовать), с пометкой «контракт не подтверждён, раздел N».
- Page objects: расширения `practical_task_page.py` (блок «Работы на проверку», форма критериев,
  результат по своей работе), `reviewer_page.py` (peer-проверки, агрегаты, итог, возврат),
  новый `external_review_page.py` (страница по ссылке без авторизации — новый browser context),
  `admin_activities_page.py` (тумблер, критерии, штатные проверяющие), `admin_programs_page.py`
  (настройки взаимопроверки в потоке). Селекторы — по разведке + пометки «уточнить после ветки».
- Тесты по кейсам этапа 1 с `- Автотест:`; тела — реальные шаги под предполагаемый контракт.
  Многоролевые сценарии — фикстуры на создание нескольких слушателей и назначение в поток
  (образец: `tests/ui/practical_tasks/test_add_listener_to_stream.py`).
- `tests/product_map.yml`: узлы `ext_pt_peer_review` («ПЗ · взаимопроверка», зона ext, рядом с
  `ext_pt`), `rev_peer_results` («Peer-проверки и итог», зона rev), `adm_pt_p2p` («ПЗ · настройки
  взаимопроверки», зона adm), `ext_external_review` («Внешняя проверка по ссылке», зона ext или
  int); рёбра к существующим `ext_pt`, `rev_pt`. Координаты не пересекать с миссией МТС Линк
  (она добавляет узлы в adm и int) — проверить после merge обеих.
- Проверка: `--collect-only` собирает; прогон без флага — только skipped; генератор кейсов не
  ругается на `docs/test_cases/p2p/`.
