# Отчёт: кейсы ai_chat — generate.py + testit_sync.py --dry-run

Задача из `docs/plans/2026-10-07_ai_chat_pmi_mission.md`, Часть 3, п.8–9. Только документация —
автотесты и код tools не менялись.

## 1. `python tools/test_cases/generate.py --area ai_chat`

Первый запуск (черновика `docs/test_cases/ai_chat.md` не было): `ai_chat: 27 тестов (новых 27,
обновить 0, без изменений 0)`.

**Найденный пробел генератора**: `pytest --collect-only` реально отдаёт 29 node id в области
`ai_chat` (проверено отдельным прямым запуском `pytest tests/api/ai_chat tests/ui/ai_chat
--collect-only`), а генератор включил только 27. Разница — оба параметризованных кейса
`tests/ui/ai_chat/user/test_player_chat_hidden.py::TestPlayerChatHidden::test_chat_button_hidden`
(ПМИ шаги 32–33, скрытая кнопка чата при выключенном чате / при удалённых документах). Причина:
значения параметра `case` — русский текст с пробелом («чат выключен», «документы контекста
удалены»); pytest по умолчанию ASCII-экранирует кириллицу в id параметризации, но пробел внутри
`[...]` остаётся как есть, и регулярка генератора `^\S+\.py::\S+$` (а также идентичная в
`testit_sync.py`) не матчит такую строку целиком — node id с этим тестом просто не попадает в
список. Это ограничение инструмента (не продуктовый дефект), чинить tools не в объёме этой задачи
(документация только) — отметил здесь, чтобы не потерялось.

**Что сделал с этим пробелом**: оба кейса добавлены в `docs/test_cases/ai_chat.md` вручную как
`TC-AI_CHAT-028`/`029`, со строкой `- Автотест:` с точным (ASCII-экранированным) node id, который
реально возвращает pytest, и с `<!-- steps-hash: e48a7d63bb18 -->`, посчитанным тем же алгоритмом
(`generate.steps_hash`) по фактическим шагам теста — повторный запуск генератора их не трогает (не
находит по тому же регэксп-пробелу — значит и не задвоит, и не затрёт правки; подтверждено повторным
прогоном, см. ниже).

**Проверка идемпотентности**: повторный `generate.py --area ai_chat` после ручной доводки файла до
читаемого вида → `ai_chat: 27 тестов (новых 0, обновить 0, без изменений 27)`, `git status` файла не
показал изменений — человеческие формулировки шагов/заголовков не перезаписались (хэш считается по
исходному коду шагов `allure.step`, не по тексту в md).

## 3. `python tools/test_cases/testit_sync.py --dry-run --area ai_chat`

Вывод: `ai_chat (Чат с ИИ в курсах): 33 кейсов (создать 33, обновить 0, ручных 6)`. План записан в
`workspace/testit_export.json` (не коммитится, значения `.env` в файл не попадают — токен туда не
пишется принципиально по коду `testit_sync.py`, а `TESTIT_PROJECT_ID`/`TESTIT_URL` в эту заметку и
в md-файл кейсов не копировались).

**Дубли**: не обнаружены — все 33 `tc_id` (`TC-AI_CHAT-001`…`033`) уникальны, у всех `existing_testit_id:
null`, `action: "create"` (ожидаемо для первого прогона — строк `- Test IT:` в md ещё нет).

**Расхождение «ручных 6» вместо ожидаемых 4**: `testit_sync.py` использует ту же регулярку
`AUTOTEST_RE` (`^-\s*Автотест:\s*(\S+)\s*$`), что и `generate.py` — по той же причине (пробел в
ASCII-экранированном node id параметра `case`, см. §1) кейсы **028 и 029** в экспортированном плане
получили `"autotest": ""`, `"manual": true` и тег `manual` вместо `autotest:<node id>`, хотя у них
за автотестом реально стоит код (строка `- Автотест:` в md корректна и читаема человеком — ломается
только парсинг инструментом). Из-за этого сводка показывает 6 «ручных» (4 реально ручных 030–033 +
2 ложно расценённых 028/029) вместо 4.

Это не блокирует `--apply`: у этих двух кейсов есть тег `tc:TC-AI_CHAT-028`/`029`, и
`find_work_item` при отсутствии `case.autotest` ищет именно по тегу `tc:<TC-ID>` — повторный
`--apply` будет находить и обновлять их корректно, не создавая дублей. Единственное следствие —
в самом Test IT у этих двух work item будет тег `manual` вместо `autotest:<node id>`, что менее
точно описывает происхождение кейса. Если это важно поправить, нужно будет либо вручную
подправить тег в Test IT после заливки, либо (отдельной задачей, не сейчас) ослабить регулярку
`AUTOTEST_RE` в `generate.py`/`testit_sync.py`, чтобы она принимала пробелы внутри `[...]`
параметризации.
