# Разведка контракта: QR-код пользователя и Рейтинги/отзывы на develop

Дата: 09.10.2026. Выполнено живыми HTTP-запросами через `api_client` (обычный requests-клиент,
без браузера) на `--env develop`, под тремя личностями: admin (`role="default"`), обычный
только что созданный слушатель (`created_user`+`assigned_user`, отдельная авторизованная
сессия через `login_user_session`) и анонимный клиент без авторизации. Скрипт разведки —
`scripts/_recon_qr_ratings.py` (одноразовый, guard `QA_RECON=1`, не часть обычного прогона).
Все созданные для разведки сущности (пользователь/программа/поток/tincan-курс) удалены
штатным teardown фикстур в конце прогона.

## QR-код

### `GET /qr-code/generate`
- admin: `200`, `Content-Type: image/png`, `Content-Disposition: attachment;
  filename="my-qr-code.png"`, тело — валидный PNG (~1.1 КБ).
- user (обычный слушатель): `200`, тот же формат — **генерирует QR текущего авторизованного
  пользователя из токена сессии, не по явному параметру `user_id`** (оба ответа структурно
  идентичны, отличается только сам PNG).
- anon: `401 {"message":"Unauthenticated."}`.

### `GET /qr-code/download`
- admin/user: `200`, `Content-Type: application/pdf`, `Content-Disposition: attachment;
  filename="my-qr-code.pdf"` (~25 КБ) — **PDF-версия того же персонального QR**, не иной набор
  данных. Отличие от `generate` — только формат файла (PNG vs PDF в обёртке страницы).
- anon: `401`, как и у `generate`.

### `POST /qr-code/parse-token`
- Без `token` (`{}` или с полем `qr_token`): `422`, обязательно поле
  **`data.attributes.token`** (JSON:API-конверт, не плоское поле `token`/`qr_token`).
- С `data.attributes.token="garbage"` (произвольная строка) — **тоже `422`** с той же
  причиной «поле обязательно для заполнения» — то есть валидатор в разведке не дошёл до
  проверки содержимого токена, он просто не видел поле на пути `data.attributes.token`
  (разведка пробовала путь `token`/`qr_token` напрямую, не через конверт — не домыслили
  конверт заранее, см. правило плана «не гадать контракт»).
- **Не проверено в этой разведке**: ответ с реально сгенерированным токеном (из PNG/PDF
  выше) в правильном конверте `{"data": {"attributes": {"token": "<реальный QR-токен>"}}}`
  — требует декодирования QR-изображения (например, `pyzbar`, которого нет в
  `requirements.txt`) или иного способа получить сырой токен до кодирования в QR. **Задача
  для Части 2/3**: либо найти токен в ответе `generate` каким-то иным полем (сейчас тело —
  чистый бинарный PNG/PDF без сопутствующего JSON с токеном открытым текстом), либо
  декодировать изображение, либо спросить у бэкенд-команды, не кодируется ли в QR просто
  такой же JWT/подписанный токен, что фигурирует в `generate`/`download` как query-параметр
  (не было передано в разведке — проверить, не нужен ли `GET /qr-code/generate?token=...`
  для «моего» vs «чужого» случая — пока наблюдали только «свой» QR текущего пользователя).

## Рейтинги/отзывы

### `GET /ratings`
- admin: `200`, пагинированный список (`meta.per_page=25`, `meta.total=65` на develop —
  **на стенде уже есть реальные отзывы**, не пустой список), без фильтров — отдаёт все
  отзывы всех сущностей сразу (не только свои). Структура элемента:
  ```json
  {
    "id": 158,
    "body": "текст отзыва или null",
    "status": 2,
    "author": { "id": 5, "attributes": { ...как у users... } },
    "rating": 5,
    "reviewer": null,
    "entity_id": 31,
    "entity_type": "knowledge_base_material",
    "entity_type_human": "",
    "entity_name": "Аудио",
    "admin_link": "",
    "created_at": "...", "updated_at": "..."
  }
  ```
  - **`status`** встречается как `0`, `1`, `2` — по наблюдаемым данным по всей видимости
    `pending`/`rejected`/`approved` либо похожий набор (сама расшифровка на стенде нигде
    не возвращается текстом — только числом; точные подписи уточнить у владельца или через
    `POST /ratings/change-status`, см. ниже про допустимые значения `status`).
  - **`entity_type`** — не всегда короткий алиас: у отзывов на материалы базы знаний это
    `"knowledge_base_material"`, но у отзыва на программу (`id=156`) это **полный
    PHP-класс** `"App\\DbLayer\\Eloquent\\Models\\Programs\\Program"`. Значит entity_type
    для создания отзыва на свежесозданный tincan-курс (Части 2/3) заранее не очевиден —
    **нужно установить эмпирически** (создать через `POST /ratings` с несколькими
    кандидатами на реальном `created_tincan`/`created_program`/`created_stream` id и
    посмотреть, какой вариант даёт `201`, а не гадать по аналогии).
  - **`reviewer`** — отдельное поле помимо `author`: у части отзывов заполнено (есть
    «проверяющий»/модератор, ответивший на отзыв), у части `null`. Это не то же самое, что
    модерация статуса — похоже, отдельный механизм комментария/ответа на отзыв.
- anon: `401`.

### `GET /ratings/my-review` и `DELETE /ratings/my-review`
- **Оба метода требуют query/body `entity_type` + `entity_id`** — без них `422`
  («Поле entity type обязательно для заполнения», «Поле entity id обязательно для
  заполнения»). То есть «мой отзыв» — это не глобальная сущность «мой последний отзыв», а
  «мой отзыв конкретно на эту сущность» (`entity_type`+`entity_id` обязательны как параметры
  запроса, не как часть JSON:API-конверта — сама разведка посылала их как есть в query/json,
  **не проверено отдельно, query это или json-body** — для `GET` вероятнее query, для
  `DELETE` тоже вероятно query, т.к. у DELETE обычно нет тела; уточнить в Части 2 при
  реализации `RatingsEndpoint.my_review`/`delete_my_review`).
- anon: `401` на обоих.

### `POST /ratings` — обязательный конверт `data.attributes.*`
- `{}` и все плоские варианты (`{"rating":5,"content_id":...}`,
  `{"value":5,"content_id":...}`, `{"rating":5,"program_id":...}`, с `comment`/`text`/`review`
  вместо текста) — **все одинаково `422`** с одной и той же ошибкой: обязательны
  **`data.attributes.rating`**, **`data.attributes.entity_type`**, **`data.attributes.entity_id`**.
  Разведка не дошла до реального успешного создания — все попытки были в плоском виде, не в
  конверте (ошибка методологии разведки, не продукта: не проверили на `{}` сначала структуру
  ошибки, прежде чем перебирать поля — в следующий раз сразу смотреть на путь поля в
  `errors`, он явно показывает нужный конверт).
  - **Правильный пример для Части 2 (ещё не проверен живым запросом, собран по форме
    ошибки)**:
    ```json
    {"data": {"attributes": {"rating": 5, "entity_type": "knowledge_base_material", "entity_id": 123}}}
    ```
  - Поле для текста отзыва (`body` по форме ответа `GET /ratings`) в payload создания не
    проверялось вообще — весь перебор был без конверта, значит все попытки одинаково упали
    на отсутствии трёх обязательных полей раньше, чем сервер дошёл бы до валидации текста.
    **Нужно повторить с правильным конвертом** и отдельно проверить, обязателен ли `body`
    (`GET` показывает отзывы и с `"body": null` — значит, вероятно, необязателен, но это
    видно из уже существующих отзывов, не из валидации создания — подтвердить фактом).

### `POST /ratings/change-status` — модерация, массовая операция
- `{}` (admin): `422`, обязательны **`data.attributes.review_ids`** (массив — «Необходимо
  выбрать хотя бы один отзыв») и **`data.attributes.status`** («Поле Статус обязательно для
  заполнения.») — **это bulk-операция над списком id отзывов**, не над одним.
- `{}` (user): `403 {"data":{"error":"У Вас нет доступа к данному разделу."}}` — **доступно
  только admin-роли** (обычный слушатель получает чистый 403, не 422 — проверка прав идёт
  раньше валидации полей). Подтверждает предположение плана: для теста модерации роль
  `role="default"` (единственная статическая учётка в `.env`) подходит, отдельная роль не
  нужна.
- Допустимые значения `status` не выяснены (нужно либо найти в фронте/документации, либо
  перебрать правдоподобные кандидаты `approved`/`rejected`/`pending` или числа `0`/`1`/`2`
  по аналогии с полем `status` в `GET /ratings` — **эмпирически в Части 2**, не гадать
  в тесте).

### `POST /ratings/export`
- admin: `{}` → **`200 {"result":"ok"}`** — синхронный, без дополнительных обязательных
  полей (в отличие от `change-status`, тут пустое тело прошло валидацию).
- **user (обычный слушатель): тоже `200 {"result":"ok"}`** — **нет проверки роли**, в отличие
  от `change-status`. Это не обязательно баг (возможно, экспорт — это просто постановка в
  очередь письма себе со своими отзывами, а не привилегированная выгрузка всех отзывов), но
  заслуживает отдельной проверки в Части 2/3: что реально приходит в результате — файл по
  email, ссылка на скачивание, то же самое для разных ролей или нет. Ответ `{"result":"ok"}`
  ничего не раскрывает о реальном побочном эффекте — **не фиксировать как «работает
  одинаково для всех ролей», пока не увидим реальный результат экспорта**.

## Итог: что можно брать в реализацию как факт, что требует доп. проверки в Части 2

**Факт, не требует перепроверки:**
- QR — персональный (текущего пользователя из токена), два формата (`generate`=PNG,
  `download`=PDF), анониму — `401`.
- `parse-token` требует конверт `data.attributes.token`.
- `ratings/my-review` (GET и DELETE) требуют `entity_type`+`entity_id`.
- `POST /ratings` требует конверт `data.attributes.{rating,entity_type,entity_id}`.
- `change-status` — bulk по `review_ids`+`status`, доступен только admin (403 обычному
  пользователю).
- `export` — синхронный `200 {"result":"ok"}` без обязательных полей.

**Требует эмпирической проверки при реализации (Часть 2), не предполагать заранее:**
1. Какой именно `entity_type` принимает сервер для tincan-курса/программы/потока —
   перебрать кандидаты на реальном `created_tincan` до первого `201`.
2. Реальный успешный `POST /ratings` (конверт есть, живой `201` с этим конвертом — нет).
3. Допустимые значения `status` в `change-status`.
4. Реальный побочный эффект `POST /ratings/export` для разных ролей (файл/ссылка/письмо).
5. Является ли «отсутствие проверки роли» в `export` осознанным поведением или дефектом —
   не заводить как баг до прояснения ожидаемого поведения.
6. `parse-token` с реальным валидным токеном (нужно получить сырой токен — из QR-изображения
   декодированием или иным путём, в разведке не найден открытым текстом).
